# Chat 核验事务与持久化恢复修复设计

## 背景与现状

根因见BUG-0068的root-cause.md E13—E15。reconcile先terminal UPDATE，再stable扫描，reader在逐卡处理后commit；零行UPDATE同样开启SQLite写事务。当前捕获线程11843/11890，历史06:53线程与失败SQL未知。方案针对已确认机制，保留原故障证据。

## 修复方案

### 1. 三阶段核验与短事务

读取阶段只获取核验所需的guard、turn、权限/项目身份与版本标量；在进入文件扫描前结束读取事务，不携带跨事务ORM可变实体。计算阶段复用已获取的稳定快照，完成解析、journal读取及结果计划，无数据库写事务。

应用阶段用短事务重新读取并校验operation_id、guard.version、state、terminal_status及权限/归属，再通过条件UPDATE应用计划。快照修订与输入指纹采用既有可信核验规则；不能在短事务内重新全量扫描，输入发生变化则拒绝旧计划并在事务外重新计算。围栏失败保持待核验，不强行释放保护或推进阶段。扫描期间的并发变化通过快照稳定性和写前轻量版本/指纹复核覆盖，不能仅提前commit后无条件写入。

terminal在已处于目标终态且原因未变化时不执行DML；需要更新时仍使用条件写，防止旧回调覆盖新operation。审计reconcile_external、completion_status等同一请求写路径，避免提前UPDATE后重新进入文件I/O。只对真实字段变化更新updated_at。

### 2. 锁错误与恢复边界

SQLITE_BUSY/LOCKED与MySQL死锁/锁等待按驱动细分码分类，其他OperationalError不冒充锁冲突。仅对已回滚、可证明未提交且无外部副作用的短数据库事务做本地有界重试：最多3次总尝试，退避50/150毫秒；仍受请求/执行剩余期限限制，每次新事务重新检查围栏。不改变既有操作级恢复次数与授权规则，不允许嵌套重试放大预算。

提交结果不明时先按唯一执行/事件身份读回；无法确认则保持unknown/待核验及现有原因码。禁止重跑模型、shell、apply或重复账务。持久化失败的诊断使用不依赖同一被锁事务的日志出口，诊断失败不得递归阻断主流程。鉴权更新时间合并不是本次必要前提，优先消除已确认长事务。

### 3. 可观测性

遵循docs/standards/product-data-collection-observability.md。记录阶段、驱动错误码、事务持续时间、尝试数、脱敏request/trace/operation关联与函数栈；不输出SQL参数、凭据或对话正文。请求计时与DB事务计时分开，不能用py-spy间隔推算完整事务时长。既有保留周期不变。

## 测试策略与验收映射

| AC | 方法与证据 |
|---|---|
| AC-001 | 实际terminal零行DML回归，记录驱动细分码和阶段；保留历史不可恢复边界 |
| AC-002 | 文件扫描屏障暂停2秒时独立写连接以200ms锁等待预算成功；至少20轮、2个context读者与1个Chat写者，零锁致中断和零重复结果；记录p50/p95、事务时长及HTTP错误率，端到端预算沿用BUG-0056而不新增未经验证的承诺 |
| AC-003 | 短锁释放和持续锁注入；最多3次本地尝试、期限可中止、不重放外部业务 |
| AC-004 | 提交前失败与提交后断连分别注入；按唯一键读回、事件/账务不重复 |
| AC-005 | 过期、撤销、冻结、跨空间拒绝及并发权限变化 |

| AC-007 | 同一并发与错误矩阵在SQLite/MySQL执行，分别保留版本及结果 |
| AC-008 | 错误/事务关联与日志脱敏断言；日志出口失效不阻断执行 |
| AC-009 | 隔离正常、失败、读回及旧回调样本，不使用原BUG-0056轮次重放 |

共享数据库故障注入与服务样本串行执行；独立临时库单测可并行。真实验收使用隔离环境与无副作用新样本，记录部署指纹；任何现有服务重启不在本次授权中。需要临时Docker时登记、打标、清理并验证零残留。单元与隔离样本不冒充真实轮次。

## 依赖与风险

BUG-0056共享reader路径：合并时联合验证快照一致性和性能，不能将其原apply完成作为本Change前提。事务拆分会引入计划过时风险，通过版本/身份围栏及拒绝重算处理；不能用无条件commit缩短事务。仅开WAL、加大timeout或切MySQL不能替代根因修复。sprint-014剩余3人天缓冲，设计扩围需重新估算。

## 文档与回滚

同步docs/04-database-design.md的事务边界、compatibility双库矩阵和API诊断说明；响应契约不变则客户端生成N/A，若改变则补OpenAPI及生成校验。发布/回滚按独立流程，不修改历史数据与保护状态。复用知识库governance-recovery-archive-evidence的证据分层与原记录保留原则。

## 实施细化

采用限定用途的VerificationPlan记录guard/观测DML；规划读取物化后结束事务，不执行写入。应用时新事务重验权限、项目代次、完整guard原值与turn终态，以条件写加围栏后原子执行计划。所有生产reconcile_external调用传actor进入该路径，旧无actor入口仅保留既有内部调用兼容。调用入口明确拥有核验事务边界，已批准的前置意图先提交；不会把该适配器用于一般业务事务。
