# Design

## 根因

用户管理页将不可见或不可操作的校验失败条件绑定到按钮 `disabled` 和提交 early return：

- 编辑用户弹窗复用新增用户 `username` 校验。编辑态用户名只读，后端更新接口不接收 `username`，但前端保存仍被 `validUsername` 阻断。
- 确认弹窗在 `reason.trim().length < 4` 时禁用确认按钮，而错误提示仅在用户输入过短内容后显示；空原因没有错误反馈。

## 修复方案

### 编辑用户弹窗

- 将用户名合法性门禁限定为新增态。
- 编辑态保存按钮不得因只读用户名不符合新增正则而禁用。
- 提交逻辑中仅在新增态检查用户名正则；编辑态保留上传中和保存中防重复提交门禁。
- 新增态的用户名错误文案和校验行为保持不回归。

### 确认弹窗

- 引入显式提交校验状态，例如用户点击确认后标记 attempted submit。
- 空原因、纯空白或不足 4 个字符时展示 `.admin-form-error` 错误文案。
- “操作原因”标签使用现有 `label.required` 样式展示红色 `*`，红星必须紧跟字段名同一行展示，让管理员在输入前即可识别该字段必填。
- 校验失败时不调用重置密码、冻结、解冻或删除 API。
- 合法原因时保持原成功流程：调用 API、关闭确认弹窗、展示 toast 或临时密码弹窗。

## 测试策略

- 前端 Testing Library 覆盖用户管理页。
- 验证编辑已有异常用户名用户时仍可保存可编辑字段。
- 验证空原因点击确认显示错误并不调用状态 API。
- 验证短原因继续显示错误且不调用 API。
- 验证合法原因保持既有成功路径。

## 影响范围

- UI：管理后台用户管理页。
- API：不变。
- DB：不变。
- 权限：不变。
- 部署：不变。
- 客户端生成：不需要。

## 知识沉淀

该问题属于后台表单/弹窗校验反馈缺陷，可复用 `admin-modal`、`admin-form` 类最佳实践；若后续多处后台弹窗复发，再沉淀到 `docs/knowledge-base/incidents/`。
