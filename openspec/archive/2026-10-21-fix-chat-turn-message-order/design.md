# Chat 消息确定性排序与分页兼容设计

## 背景与现状

根因来自 BUG-0055 E3—E6：admission 分别取得轮次和用户消息身份；persist_output 使用 turns.created_at；message_page 覆盖助手时间后做 offset 分页；ConversationMessages.merge 先比较 created_at。稳定助手 ID 已由 message_id(turn_id) 生成，可复用。BUG-0030 仅是模块关联，BUG-0052 不是本次根因。

## 修复方案

### 1. 确定性总顺序

消息响应新增结构化 `order_key`，字段为 `turn_created_at`、`turn_id`、`role_rank`、`message_id`。正向按该四元组升序：user=0、assistant=1，其余合法角色按显式固定枚举排后。同秒多轮按稳定 turn_id 排序；这只提供确定性，不声称同秒真实发生顺序。后端 SQL 使用同一四元组的严格逆序分页，前端按正序展示，禁止以 created_at 优先覆盖轮内顺序。

虚拟助手在 SQL 分页前即采用最终稳定 ID；不得在排序/limit 后才补 ID。旧助手已有 ID 保留，复用现有权威消息选择规则；不同历史消息不得仅因同轮而合并丢失。SQL 字符串比较与客户端按 ASCII 标识逐字节比较对齐，时间统一 UTC 精度；SQLite/MySQL 排序规则需实测。turn 创建时间保持不可变，不用 updated_at 排序。

### 2. 消息时间来源

停止把所有助手 created_at 覆盖为轮次开始时间。新持久消息 created_at 记录首次保存时间，重复恢复只更新内容及 updated_at，保持首次保存时间。新增 `display_time`（可空）与 `time_source`（message_saved、output_event、legacy_unknown）。虚拟消息使用首个可靠助手输出事件时间，明确它是输出记录时间；不把 final 或 updated_at 伪装成首次回复时间。

历史助手存储时间保留；若现有时间等于轮次开始且不能可靠区分旧投影与真实保存，保守归为 legacy_unknown，display_time=null，页面显示“历史回复时间未确认”。有可靠输出事件时可展示首个保留事件的记录时间及来源（不保证是已裁剪历史中的首次输出），不能改写原行。用户显示消息保存时间。created_at 保留兼容字段，不再作为展示排序依据；API 明确历史该字段可能是旧轮次时间。新写入也无法可靠证明来源时同样保守降级，不凭时间相等断言真实时序。事件被裁剪时不从邻近消息推算时间。

### 3. 分页及并发收敛

保留 page/page_size 旧入口，新增可选 `before` 游标，响应新增 `next_cursor`、`has_more`。游标为版本化四元组及 conversation_id 的受限编码，服务端校验类型、长度、版本和会话一致性；游标不承担授权，所有查询先检查会话访问权。使用参数化字典序小于条件，SQL 排序后再 limit。旧 page 入口按相同总顺序返回，但并发收敛保证由新 Web 游标协议提供。

单纯 keyset 无法发现已越过游标的旧轮次新增输出，因此 Web 保留已加载最早边界，周期性从最新页向该边界做游标复核，按消息身份更新合并；新输出、持久化、恢复及重连触发复核。每个请求受 page_size 限制，深页每250ms串行续接，深扫描期间每3秒穿插最新页读取，上一轮完成前不启动重叠全范围扫描，不能每次轮询都取消未结束的深页复核。无变化时降低复核频率；后续任务需覆盖深历史请求数量预算，避免重复逐轮请求。

每轮复核有会话 generation 和请求序号，旧会话响应丢弃；同一 ID 较旧响应不得覆盖较新内容，终态内容以服务端新鲜复核为准。加载更多的游标与复核队列独立，保持滚动锚点。数据停止变化后一次完整范围复核应收敛至相同范围的后端全集；持续写入期间不承诺事务快照，显示加载状态，不能错误宣告历史完整。已加载边界之外的迟到输出随正常加载更多出现。

### 4. 兼容与安全

不修改表结构或历史记录，复用现有事件时间、轮次和消息事实；API 新字段同步 OpenAPI 与生成客户端，前后端配套部署。旧服务缺字段时 Web 进入明确兼容状态，不把不完整元数据视为新契约已通过。所有查询保留租户/会话权限、恢复幂等、部分输出和截断标识；无消息正文泄漏，不增加权限或业务状态转换。

## 测试策略

按 acceptance.md 映射 BUG 全部12项 AC。后端使用可控时钟与 API 分页全集比较；前端使用真实接口形状验证合并、迟到响应与身份转换；SQLite 与 MySQL 验证排序、分页及持久化语义。部署观察使用通用样本发送、输出、刷新、分页及恢复，历史归档仅只读。合成回归不能冒充真实观察。

## 风险与取舍

- 只改前端会保留服务端分页错误；只按时间相等角色排序不能覆盖跨秒，均不采用。
- 全量改历史时间会伪造事实；本方案保留数据并显式降级。
- 游标加范围复核增加读取成本，需请求计数与深页预算验证，避免与历史逐轮重放问题叠加；本 Change 不扩展为整体性能重构。
- 数据库排序表达式可能影响索引，实施阶段评估计划与真实兼容性后决定是否需要索引；发现迁移需求先更新设计及容量。

## 发布与回滚

先验证服务新字段兼容旧客户端，再部署配套 Web；不自动执行生产变更。回滚配套应用，保留新增消息和时间事实。无 schema 迁移时无数据回滚；不能为了恢复旧界面去还原数据库内容。

## 实施验证边界

不新增数据库字段、索引或迁移，真实 MySQL 8.2 与 SQLite 均通过消息排序和既有输出回归。正常回复和停止样本来自用户授权的两次隔离测试提示，分页历史为显式合成数据；原 REQ-0046 倒置样本只读核验，原记录哈希不变。完整证据见 verification.md。
