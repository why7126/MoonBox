## ADDED Requirements

### Requirement: 管理后台用户列表
系统 SHALL 在管理后台提供用户管理列表页，用于查看平台用户账号及其账号生命周期状态。

#### Scenario: 查看用户列表
- **WHEN** 后台管理员进入用户管理页面
- **THEN** 系统从后台用户 API 读取真实用户分页数据，并展示头像、用户名、昵称、角色、状态、空间数、最近登录时间、创建时间和操作列
- **AND** 默认列表 SHALL 不展示 `status=已删除` 的逻辑删除用户

#### Scenario: 筛选用户
- **WHEN** 后台管理员输入用户名或昵称关键词，或选择角色、状态筛选条件
- **THEN** 系统将当前筛选条件提交给后台用户 API 并自动刷新用户列表，且角色筛选仅包含“后台管理员”和“前台用户”
- **AND** 状态筛选 SHALL 仅提供“全部状态”、“待激活”、“正常”和“已冻结”，不得提供“已删除”筛选项
- **AND** “全部状态” SHALL 不展示 `status=已删除` 的逻辑删除用户
- **AND** 后台用户 API 返回的 `total` SHALL 使用与当前列表相同的逻辑删除筛选规则计算

#### Scenario: 用户列表分页
- **WHEN** 用户列表超过当前每页条数
- **THEN** 系统使用后台用户 API 返回的用户总数展示左侧用户总数，并展示右侧上一页、下一页、页码、“每页显示”文案和条数下拉框

### Requirement: 用户创建与编辑
系统 SHALL 支持后台管理员通过弹窗创建用户，并编辑用户头像、昵称和角色。

#### Scenario: 创建用户
- **WHEN** 后台管理员提交包含用户名、头像、昵称和角色的创建表单
- **THEN** 系统校验用户名全局唯一、4-32 位、仅允许字母和数字且必须以字母开头，并在成功后创建待激活用户
- **AND** 系统生成一次性临时密码、写入后端 `password_hash`，并通过临时密码弹窗仅在本次创建结果中展示一次

#### Scenario: 编辑用户
- **WHEN** 后台管理员编辑已有用户
- **THEN** 系统将用户名只读展示，并仅允许修改头像、昵称和角色

#### Scenario: 防重复提交
- **WHEN** 后台管理员重复触发创建或编辑提交
- **THEN** 系统 SHALL 防止产生重复用户或重复写操作

### Requirement: 用户状态治理
系统 SHALL 支持后台管理员冻结、解冻和逻辑删除用户，并保留审计追溯所需数据。

#### Scenario: 冻结用户
- **WHEN** 后台管理员确认冻结用户并填写原因
- **THEN** 系统冻结目标用户，并使目标用户全部有效会话在 10 秒内失效

#### Scenario: 解冻用户
- **WHEN** 后台管理员确认解冻已冻结用户并填写原因
- **THEN** 系统恢复目标用户可用状态，并记录该状态变更

#### Scenario: 逻辑删除用户
- **WHEN** 后台管理员确认删除用户并填写原因
- **THEN** 系统将用户标记为已删除，保留审计追溯数据，且不执行物理删除

### Requirement: 密码重置
系统 SHALL 支持后台管理员重置普通用户密码，并保护临时密码或重置结果。

#### Scenario: 重置密码
- **WHEN** 后台管理员确认重置普通用户密码并填写原因
- **THEN** 系统生成一次性临时密码、写入后端 `password_hash`、撤销目标用户现有会话、记录审计，并通过临时密码弹窗仅展示一次临时密码或重置结果

#### Scenario: 敏感结果保护
- **WHEN** 系统返回临时密码或重置结果
- **THEN** 系统不得将该敏感结果写入日志、埋点或前端持久化存储
- **AND** 前端 SHALL 在弹窗中提供复制按钮，关闭弹窗后清空临时密码状态且不得再次展示

### Requirement: 系统内置超级管理员保护
系统 SHALL 保护唯一系统内置超级管理员账号，防止其被管理后台误操作。

#### Scenario: 展示超级管理员
- **WHEN** 用户列表包含系统内置超级管理员
- **THEN** 系统展示“系统内置”或等价标识，并显示不可操作状态

#### Scenario: 禁止超级管理员写操作
- **WHEN** 后台管理员尝试编辑、重置密码、冻结、解冻或删除系统内置超级管理员
- **THEN** 系统拒绝该操作，且前端不得提供有效操作入口

### Requirement: 用户头像上传
系统 SHALL 支持用户头像上传，并在同一会话中即时回显上传结果。

#### Scenario: 上传头像
- **WHEN** 后台管理员在创建或编辑用户弹窗中上传头像
- **THEN** 上传组件进入 `idle -> uploading -> done/failed` 状态机，并在上传中禁用重复提交

#### Scenario: 头像即时回显
- **WHEN** 头像上传成功
- **THEN** 系统在当前弹窗和用户列表中立即回显头像，不要求刷新页面

#### Scenario: Docker 本地对象存储访问
- **WHEN** 在 Docker 本地 `:3000` 环境完成头像上传
- **THEN** 系统 MUST 将头像对象写入 MinIO 单 Bucket 的 `images/avatars/{uuid}.{ext}` 前缀
- **AND** 浏览器 MUST 通过授权后的后台读取接口读取并回显该头像对象

### Requirement: 用户管理审计
系统 SHALL 为用户管理写操作记录审计信息。

#### Scenario: 写操作审计
- **WHEN** 后台管理员创建、编辑、冻结、解冻、删除用户或重置密码
- **THEN** 系统记录操作者、操作对象、动作、前后值、原因、结果、时间和请求 ID

### Requirement: 用户管理 UI 横切一致性
系统 SHALL 遵循 MoonBox 管理后台 UI 规则和用户管理横切验收要求。

#### Scenario: 状态操作确认
- **WHEN** 后台管理员触发冻结、解冻、删除或重置密码
- **THEN** 系统使用设计系统确认弹窗，且不得调用 `window.confirm`

#### Scenario: Toast 不位移
- **WHEN** 用户管理页面展示成功或失败反馈
- **THEN** 系统使用 fixed toast，且不得引发布局位移或挤压列表、分页、弹窗内容

#### Scenario: 弹窗宽度与滚动
- **WHEN** 新增或编辑用户弹窗在桌面或低视口打开
- **THEN** computed width 与设计预期一致，弹窗 body 可滚动，底部操作按钮可访问
