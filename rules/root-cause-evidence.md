# 证据化根因分析治理

## 1. 目标

问题排查、BUG 完善、验收返修、效果不如预期、发布或部署异常时，AI MUST 先建立证据链，再确认根因。根因不能靠猜测；没有日志、复现、截图、测试失败、代码定位、配置差异、数据样本或运行时观测证据时，MUST 保持为待验证假设或未知状态。

## 2. 根因状态

| 状态 | 含义 | 门禁 |
|---|---|---|
| `unknown` | 证据不足，无法形成有效假设 | 先按第 5 节自主取证；仍缺关键证据时输出人工补证步骤；不得进入修复评审 |
| `hypothesis` | 有方向性推测，但缺少关键证据 | MUST 标注为假设；不得写成已确认根因 |
| `probable` | 有间接证据，但仍需补关键验证 | SHOULD 继续补证；除 P0 热修外不得通过 BUG review |
| `confirmed` | 证据链可复核，能解释现象和触发条件 | 仅满足根因门禁；评审、Sprint、Change 和实现仍分别遵循流程与授权 |

AI MUST NOT 将 `unknown`、`hypothesis` 或 `probable` 表述为“已确认根因”。如因 P0 热修需要基于 `probable` 先做 workaround，MUST 明确记录热修理由、证据缺口、回滚方案和补证任务。

### 2.1 BUG 根因连续补证

`/bug-explore`、`/bug-generate`、`/bug-complete` 在发现根因仍为 `unknown`、`hypothesis` 或 `probable` 时，MUST 在当前命令内继续尝试取得足以确认或排除假设的最小关键证据；生成或更新文档不是停止取证的条件。先复用现有 capture、失败测试、代码路径、脱敏日志和配置差异，再按第 5 节在已有权限内直接访问产品复现并采集浏览器证据；只读取当前 BUG 相关范围，不为猜测根因扩大到无关目录或客户数据。

每次取得新证据后，MUST 对照现象、触发条件和代码/配置路径复核假设，记录证据来源、支持或排除的判断及剩余缺口。证据链足以解释现象与触发条件时，才能将根因标记为 `confirmed`；文档生成成功、浏览器复现成功或单条间接证据本身都不自动等于根因确认。仍无法确认时，保留真实状态、已尝试的取证路径和具体障碍，按第 5 节请求剩余人工补证，不得为了推进评审伪造 `confirmed`。

`/bug-explore` 默认只输出探索结论和证据摘要，不因自主取证而擅自生成 `bug.md` 或 `root-cause.md`；`/bug-generate` 的文档输出仍限 `bug.md`，可在其中记录已取得的证据和待验证根因，但不提前生成 `root-cause.md`；`/bug-complete` 将证据链、排除假设和结论回填 `root-cause.md`，确认后运行根因校验，再决定是否推进 `pending_review`。

### 2.2 确认范围与停止条件

调查开始或续接时声明待证命题、触发条件、环境/版本、最小直接证据和明确不覆盖事项。分别判断：可复现机制、历史单次事件的精确归因、修复有效性；三者不能互相替代。命题调整须记录旧命题、原因及未解决事项，不得为达到 confirmed 删除原问题的关键现象或反证。

机制与真实触发条件已有直接证据且无未解释的关键反证时，可在限定范围确认；历史缺失且不可追溯的分段占比继续标为未知，不要求无限重放历史请求。若关键触发条件、同请求身份或主要耗时仍未闭合，保持 probable 并按 §2.1 继续最小补证。只有截图 Waiting、独立微基准或任意夹具，不满足机制确认。

停止前逐项判断：有可执行且能消除关键不确定性的授权操作则继续；现有观测缺字段则按 §5.8 升级；同一路径无新信息则停止原样重试，切换方法；必要操作受权限或环境阻塞则报告具体缺口，继续不受阻部分；限定命题已闭合则结束该轮诊断，保留未知事项和修复验收任务。文档完成、工具成功、采样次数或时间耗尽均不是根因确认依据。确认不自动授权评审或修复，用户要求不推进时保持 Issue 阶段。

详细计时边界、诊断检查清单与正反例见 [根因诊断与证据闭环](../docs/standards/root-cause-diagnostics.md)。

## 3. 证据链

`confirmed` 根因 MUST 至少包含一条直接证据，并 SHOULD 包含复现或验证闭环。证据记录 SHOULD 使用表格：

```md
| id | type | source | 摘要 | 支持的判断 |
|---|---|---|---|---|
| E1 | test_failure | `uv run pytest ...` | 某断言稳定失败 | 证明 X 输入触发 Y |
```

允许的证据类型：

| type | 说明 |
|---|---|
| `reproduction` | 复现步骤、账号角色、入口、输入、期望/实际 |
| `test_failure` | 测试命令、失败用例、断言、堆栈关键段 |
| `runtime_log` | 后端日志、容器日志、trace_id、request_id、时间段 |
| `browser_console` | Console error/warning、页面路由、触发动作 |
| `network_request` | method、path、status、request/response 摘要、trace_id |
| `screenshot` | 截图/录屏、视口、页面状态、标注结论 |
| `computed_style` | 选择器、视口、关键 CSS 属性、实际值和期望值 |
| `data_sample` | 脱敏记录、查询结果、迁移状态、数据版本 |
| `config_diff` | 环境变量名、Compose、端口、feature flag、版本差异，敏感值脱敏 |
| `code_path` | 文件、函数、分支、异常路径或 diff 摘要 |

证据 MUST 可复核、可定位、已脱敏。MUST NOT 在文档、日志、截图说明或脚本输出中保存真实密码、Token、Cookie、Authorization header、真实 `.env` 原文、真实客户数据、未脱敏日志、本机绝对路径、系统用户名或用户主目录。

## 4. root-cause.md 模板

BUG 的 `root-cause.md` SHOULD 使用以下结构：

```md
# 根因分析

## 根因状态
status: confirmed

## 现象
- ...

## 证据链
| id | type | source | 摘要 | 支持的判断 |
|---|---|---|---|---|
| E1 | ... | ... | ... | ... |

## 已排除假设
| 假设 | 排除证据 |
|---|---|
| ... | ... |

## 已确认根因
...

## 修复方向
...

## 验证闭环
...
```

`status: confirmed` 缺少 `## 证据链` 或缺少有效证据项时视为不通过。若状态为 `unknown`、`hypothesis` 或 `probable`，MUST 在文档中保留已尝试的自主取证、证据缺口和仍需人工补证的具体步骤。

### 4.1 当前结论与历史证据

当前 root-cause.md 保留唯一有效状态、确认范围、证据索引、已排除范围、剩余未知和修复验证状态。状态变化时同步 bug.md、trace.md 当前摘要和 acceptance.md 的诊断进展，但不把诊断完成标为修复验收通过。历史判断保留原时间、证据 ID、环境和当时结论，放在明确的历史区或链接到独立调查历史；标明已被哪一当前结论替代。不得删除不利证据、重写历史采样结果，或让历史“待补”冒充当前任务。

## 5. 自主取证与人工补证契约

### 5.0 浏览器失败重试与无法访问判定

需要运行态证据时，先检查已打开的浏览器窗口和目标产品标签页，优先检查 Codex 侧边浏览器；清单获取超时或失败时，再尝试按浏览器应用名直接连接现有窗口。当前入口失败后，检查已提供的其他浏览器或等价自动化入口。一次清单超时、单个浏览器失败或终端 HTTP 探测失败，都不足以断言产品无法访问；终端与浏览器可能处于不同网络或会话环境。

对已打开页面，先记录路由、浏览器、操作和脱敏的可见结果。已加载的旧页面只能证明页面当时的展示；若结论依赖服务当前可用、最新数据或请求响应，须在授权范围内刷新页面或观察相关请求，并区分刷新成功、失败和未尝试。不要因刷新可能失败而丢弃已有页面展示证据，也不要把旧页面当作当前服务连通性证据。

工具出错后应复核错误并尝试至少一条可行的替代路径；同一路径重复失败且无新修复方向时停止原样重试。只有可用浏览器与替代入口均不可用、权限不足、必要操作超出授权，或自主取证后关键证据仍不足，才将相应范围判为阻塞并请求人工补证。报告必须分别说明：已验证的页面事实、未验证的运行态事实、逐项尝试的入口与错误、仍缺的证据；不得以“浏览器不可用”概括一次工具调用失败。

需求与通用探索、测试、验收、BUG 复现与补证、UI 对照或问题排查需要产品运行态证据时，AI 可直接使用已有权限和工具通过浏览器访问产品并完成操作、截图、Console、Network、computed style 等取证，无需再次请求用户确认；优先复用 Codex 侧边浏览器中的目标产品标签页；该入口不可用或不能取得所需证据时，使用已提供的其他浏览器或等价自动化工具，Firefox 作为后备。应先确认目标环境与当前任务相关，复用现有会话或已授权的测试账号；不得为了取证索要、读取或落盘密码、Cookie、Token 等凭证。

`/explore` 与 `/req-explore` 若结论依赖当前产品页面、流程、交互、状态或权限的真实表现，且现有材料不能确认事实，MUST 在当前探索中主动浏览产品并采集最小相关证据，再给出判断或方案；不因探索命令默认不落盘而跳过取证。浏览器浏览、页面状态查看和不产生持久业务写入的交互属于只读探索。无法访问或必要取证超出已有授权时，说明已尝试路径、证据缺口与结论不确定性，再请求具体补证；不得把推测当成已验证的现状。

浏览器取证遵守当前任务与账号权限边界。可执行页面浏览、复现、测试数据操作和可逆交互；涉及生产数据的删除、对外发送、付款、发布、权限授予等高影响或不可逆动作，仍按对应授权和环境规则处理。记录页面路由、环境、浏览器、视口、操作、时间及脱敏后的实际结果；证据按 `rules/document-governance.md` 的临时与长期存放边界处理。不能访问产品、权限不足、环境不可用、复现会改变不可逆状态，或自主取证后仍缺关键证据时，才转入人工补证，并明确已尝试路径与具体障碍；不得把可自行取得的浏览器证据默认转交用户。

AI 自主取证后仍判断证据不足时，MUST 输出可执行的补证指引，而不是泛泛要求“提供日志/截图”。补证指引 MUST 包含：

```text
待补证项：
- 证据名称
- 为什么需要
- 操作步骤
- 需要返回的字段
- 脱敏要求
- 返回格式
```

### 5.1 浏览器 Console

操作步骤：

1. 打开出问题页面。
2. 按 F12 或右键检查，进入 Console。
3. 清空 Console。
4. 重复触发问题。
5. 复制红色错误；warning 仅在相关时提供。
6. 将 token、手机号、邮箱、真实用户 ID 替换为 `<REDACTED>`。

返回字段：页面路由、操作步骤、Console 错误文本、出现时间。

### 5.2 Network 请求

操作步骤：

1. 打开 DevTools Network。
2. 勾选 Preserve log。
3. 重复触发问题。
4. 选中失败或异常请求。
5. 复制 method、path、status、request payload 摘要、response body 摘要、trace_id/request_id。
6. 不要提供 Authorization header、Cookie 或完整 Token。

返回字段：请求 method/path/status、响应摘要、trace_id/request_id、触发动作。

### 5.3 后端或容器日志

操作步骤：

1. 确认问题发生时间段。
2. 获取该时间段后端或容器日志。
3. 优先按 trace_id、request_id、用户 ID 占位符或 API path 过滤。
4. 只提供异常堆栈关键段和上下文摘要。
5. 脱敏连接串、密钥、密码、Token、Cookie、真实邮箱、手机号和客户数据。

返回字段：时间段、服务名、相关 path 或 trace_id、错误摘要、关键堆栈片段。

### 5.4 UI 视觉或交互偏差

操作步骤：

1. 记录页面路由、浏览器、视口尺寸。
2. 截取实际页面和期望参照图，标注偏差区域。
3. 对关键元素提供选择器或可定位描述。
4. 如偏差与字号、颜色、间距、层级有关，提供 computed style。
5. 若涉及交互，补充 hover/open/active/disabled 等状态截图。

返回字段：页面、视口、期望/实际截图、偏差描述、选择器、computed style。

### 5.5 数据异常

操作步骤：

1. 明确异常记录 ID 或业务键。
2. 查询相关脱敏字段、状态、更新时间、迁移版本。
3. 提供期望数据和实际数据差异。
4. 不提供真实客户姓名、手机号、邮箱、订单原文或敏感业务内容。

返回字段：记录标识、查询条件、脱敏结果、期望/实际差异、查询时间。

### 5.6 部署或环境异常

操作步骤：

1. 记录部署方式、本地/生产、镜像或提交版本。
2. 提供服务状态、健康检查结果、端口映射和配置差异。
3. 提供启动日志或失败命令摘要。
4. 环境变量只提供变量名和差异说明，不提供真实值。

返回字段：环境、版本、服务状态、健康检查、配置差异、日志摘要。

### 5.7 权限或登录问题

操作步骤：

1. 记录账号角色，不提供密码。
2. 记录入口路径和操作步骤。
3. 提供失败请求状态码、错误码、trace_id。
4. 提供服务端鉴权日志摘要，脱敏凭证。

返回字段：角色、入口、操作、请求状态、错误码、trace_id、日志摘要。

### 5.8 从观测缺口升级到受控诊断

先列已测字段、缺失字段及其阻断的判断。不存在的 span 不能靠重复查询还原；按最小风险选择原路由隔离采样或必要的受控在线采样。明确每种证据只能回答的问题，保留真实认证、数据库、负载与夹具差异。复用已有诊断授权；如涉及尚未覆盖的共享服务中断，单独协调运行安排，不重复索要同一诊断权限。

诊断前记录目标身份规范化、采样边界、时间/数量限制、数据最小化、原件摘要、恢复方式及失败处理。先取得一个请求身份和阶段完整的有效样本再扩量。计时关联响应、服务准备和审计的同一 request_id；重用会话 ID 或近似时长不足以关联。单调时钟记录嵌套关系，不重复累加父子阶段；SQL 执行耗时不能直接称为锁等待，缺失值不能记零。

结束或失败均核对原件与并发修改、移除本次钩子及专属残留、健康和入口恢复；无法恢复时报告影响与精确恢复步骤，不声称完成。永久埋点或业务修复仍走已评审 Issue、Sprint、Change，不借临时诊断绕过流程。操作清单与恢复边界见上述标准。

## 6. 工作流门禁

- `/explore` 和 `/bug-explore`：证据不足时先自主取证并复核假设；仍不足时 MUST 输出 `unknown/hypothesis/probable`、已尝试路径和人工补证步骤，不得确认根因。
- `/bug-generate`：生成 `bug.md` 后若根因未确认，MUST 在当前命令内继续自主补证并将结果回填 `bug.md`；不得借此提前生成 `root-cause.md`。
- `/bug-complete`：写入 `root-cause.md` 后若仍未确认，MUST 在当前命令内继续自主补证并回填；仍不足时停留在探索或补齐阶段，不得推进 `pending_review`。
- `/bug-review --approve`：SHOULD 先确认 root-cause evidence gate 通过。
- `/bug-opsx`：BUG 未完成证据化根因时不得创建 fix Change。
- `/opsx-apply <BUG-full-id>`：实现前 MUST 运行或等价执行 `python scripts/validate-root-cause-evidence.py --bug <BUG-full-id>`。
- `/opsx-modify`：验收返修和效果不如预期 MUST 先记录偏差证据；可通过浏览器自主补证，仍不足时输出人工补证步骤。

## 7. 测试、日志与 UI 验收

- BUG 修复 MUST 添加复现或回归测试；无法自动化时 MUST 说明原因并提供替代证据。
- 测试通过只是验证结果，MUST NOT 替代根因证据。
- 日志和错误响应 SHOULD 支持 trace_id/request_id 或等价关联字段。
- UI 偏差 MUST 使用截图、视口、关键交互状态和 computed style 或等价证据定位。

## 8. 校验脚本

项目 SHOULD 提供：

```bash
python scripts/validate-root-cause-evidence.py --bug <BUG-full-id>
python scripts/validate-root-cause-evidence.py --change <change-id>
python scripts/validate-root-cause-evidence.py --all-active
```

脚本用于结构化校验，不替代人工判断；脚本失败时，AI MUST 输出缺失项和补证建议。
