# 后台管理用户菜单栏个人资料功能

## 背景

MoonBox 管理后台已具备登录认证、后台用户管理、头像上传和用户菜单栏基础入口，但当前用户菜单栏中的“个人资料”仍是占位反馈，当前登录用户无法从全局菜单中自助维护自己的头像和昵称。

随着后台管理功能增多，管理员需要在不进入用户管理列表、不编辑角色或账号状态的情况下，快速维护个人展示信息。本需求聚焦后台管理用户菜单栏中的个人资料能力，仅允许当前登录用户修改自己的头像和昵称，并在保存后更新后台全局用户展示。

## 目标用户

- 超级管理员：需要维护个人头像和昵称，便于后台全局区域和审计上下文中识别当前操作者。
- 后台管理员：需要从用户菜单栏快速打开个人资料，并自助更新头像和昵称。
- 后台功能使用者：需要在用户菜单、表单和后续后台协作场景中看到更清晰的操作者展示信息。

## 范围

### 包含

- 用户菜单栏“个人资料”入口从占位反馈升级为弹窗入口。
- 个人资料以弹窗 Modal 形态打开，保持后台现有用户管理表单弹窗交互风格。
- 当前登录用户可以修改自己的头像。
- 当前登录用户可以修改自己的昵称。
- 昵称非必填，最长 128 个字符，规则与现有后台用户管理中的昵称字段保持一致。
- 新增或扩展当前用户专用资料更新接口，仅允许更新当前登录用户自己的头像和昵称。
- 保存成功后刷新当前登录用户摘要，并更新用户菜单栏中的头像、昵称或用户名展示。
- 头像上传沿用现有头像上传能力和对象存储配置，保存时应使用持久可访问的头像 URL。
- 头像上传交互参照当前创建用户表单的头像组件：单个头像预览位、右侧说明文案和上传/更换按钮、隐藏文件选择控件。

### 不包含

- 不支持修改用户名、角色、状态、空间数、最近登录时间或是否系统内置超级管理员。
- 不支持修改密码；用户菜单栏密码修改由 REQ-0010 承接。
- 不支持管理员在个人资料弹窗中编辑他人资料。
- 不支持头像裁剪、旋转、滤镜、美化、批量上传或图库选择。
- 不新增用户管理列表、角色权限、审计查询或通知能力。
- 不覆盖普通 Web 前台用户、小程序、移动端或桌面端个人资料。

## 功能要求

### FR-001 用户菜单栏个人资料入口

管理后台 MUST 在当前用户菜单栏中提供“个人资料”菜单项。

用户点击“个人资料”后，系统 MUST 打开个人资料 Modal，而不是仅展示 toast 或无操作反馈。个人资料 Modal SHOULD 展示当前登录用户的用户名、角色摘要、单个头像预览位和昵称输入项。

个人资料入口 SHOULD 与“密码修改”“界面主题”“退出登录”等菜单项保持同一视觉体系，但不得与密码修改混成同一个表单。

### FR-002 当前用户资料读取

系统 MUST 能读取当前登录用户的最新资料摘要，用于展示头像、昵称、用户名、角色和账号状态等只读信息。

当前用户资料读取 MUST 以后端认证结果解析出的当前用户为准，不得信任前端传入的 `user_id`、`role`、`is_admin` 或等价身份字段。

当登录态失效、会话撤销、账号不可用或凭证无效时，当前用户资料读取 MUST 返回受控认证错误，并触发前端已有登录态失效处理。

### FR-003 当前用户资料更新接口

系统 MUST 提供当前用户专用资料更新接口，用于修改当前登录用户自己的头像和昵称。

该接口 MUST 只接受头像 URL 和昵称字段，不得接受角色、状态、用户名、密码、空间数或其他用户管理字段。后端 MUST 使用认证上下文中的当前用户 ID 作为更新目标，不得允许请求体指定任意目标用户。

资料更新成功后，接口 MUST 返回更新后的当前用户资料摘要。资料更新失败时，系统 MUST 返回受控错误文案，不得泄露数据库错误、对象存储内部路径、堆栈或敏感配置。

### FR-004 头像修改

个人资料 Modal MUST 支持当前用户上传或更换头像。

头像上传 SHOULD 沿用现有后台头像上传能力，支持 JPG、PNG、WEBP，单文件大小不超过 2MB，并使用对象存储头像前缀配置保存。

头像上传成功后，前端 MAY 使用临时 object URL 做即时预览，但最终保存到用户资料中的 avatar_url MUST 是后端返回的持久头像 URL，不得保存仅当前浏览器有效的 `blob:` URL。

如果头像上传失败、文件类型不支持、文件过大或头像资源读取失败，系统 MUST 在 Modal 内给出受控错误提示，并允许用户重新选择文件。

### FR-005 昵称修改

个人资料 Modal MUST 支持当前用户修改昵称。

昵称非必填，最长 128 个字符。用户清空昵称时，系统 MUST 保存为空值或等价空状态，并在用户菜单栏中回退展示用户名。

昵称保存时 SHOULD 去除首尾空白。昵称校验失败时，系统 MUST 在 Modal 内提示用户修正，不得提交无效数据。

### FR-006 保存、取消与反馈

个人资料 Modal MUST 提供保存和取消操作。

用户点击取消或关闭 Modal 时，系统 MUST 放弃未保存的昵称和头像变更。用户点击保存时，系统 MUST 在保存期间禁用重复提交，并展示保存中状态。

保存成功后，系统 MUST 给出明确成功反馈，并刷新用户菜单栏展示。保存失败时，系统 MUST 保留用户已输入内容，提示失败原因，并允许用户修正后重试。

### FR-007 当前用户展示刷新

个人资料保存成功后，前端 MUST 更新当前登录用户摘要，确保用户菜单栏头像、昵称或用户名展示与后端返回结果一致。

如果当前会话本地缓存了用户摘要，系统 MUST 同步刷新缓存，避免页面刷新后又显示旧头像或旧昵称。

用户菜单栏展示 SHOULD 优先显示昵称；昵称为空时回退显示用户名。头像为空时 SHOULD 使用用户名或昵称首字母生成默认头像展示。

### FR-008 创建用户头像交互复用

个人资料 Modal 的头像上传区 MUST 参照当前创建用户表单中的头像交互结构：左侧仅一个 `admin-avatar large` 等价头像预览位，右侧提供格式提示和“上传/更换”按钮，并通过隐藏 file input 触发文件选择。

个人资料 Modal MUST NOT 同时展示身份摘要头像和上传区头像两个头像图标。用户名和角色摘要可以用文本展示；头像只在头像上传区出现一次。

头像按钮文案 MUST 与当前头像状态一致：无头像时展示“上传”，已有头像或已选择头像时展示“更换”，上传中展示“上传中”并禁用重复选择。

## UI 约束

- 个人资料使用 Modal 形态，不新建独立页面或抽屉。
- Modal 内只展示当前用户个人资料相关字段，避免引入用户管理列表中的角色、状态、删除、冻结、重置密码等操作。
- 头像区域应提供当前头像预览、上传或更换按钮、格式和大小提示，以及上传失败提示。
- 昵称输入应保持简洁，不需要复杂说明文案；错误提示应贴近输入区域。
- 头像区域必须复用创建用户表单的单头像预览位 + 右侧按钮说明结构，不得出现两个头像图标。
- 保存、取消按钮应与现有后台弹窗按钮层级一致，保存为主操作。
- Modal 在桌面后台场景下应居中或按现有后台弹窗规范展示，不遮挡不可恢复状态，不造成文本重叠。

## 关联需求

- REQ-0004-admin-user-management：已提供后台用户模型、昵称、头像字段、用户列表和头像上传基础能力；本需求只允许当前用户维护自己的头像和昵称。
- REQ-0005-admin-auth-system：提供当前登录用户身份、会话校验和 `/api/v1/admin/auth/me` 当前用户读取能力基础。
- REQ-0010-admin-user-menu-password-change：同属用户菜单栏能力，但负责密码修改；本需求不处理密码。
