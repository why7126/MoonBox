# 聊天框新增 Agent、模型和推理程序选择

## 1. 背景与价值

Chat 工作台已经支持用户在 MoonBox 内通过 Codex 进行持续对话和真实执行。当前聊天输入区的执行配置仍以固定 Codex 接入为主，用户无法在发送前明确查看或调整本轮对话使用的 Agent、模型和推理程序。

用户本次反馈：“聊天框新增 Agent 选择（当前有且只有一个 Codex），新增模型和推理程序的选择（类似 Codex 聊天框）”。这说明 Chat 工作台需要把执行配置前置到聊天框，让用户在发起对话前知道“由谁执行、用什么模型、采用什么推理强度或推理程序”，并确保选择结果进入后续执行链路，而不是仅作为前端静态展示。

本需求是 REQ-0025 Chat 工作台的输入区能力增强，首版不改变 Chat 工作台个人私有、服务端执行、同会话串行、权限校验和真实事件展示边界。

## 2. 目标用户

- 产品负责人：在发起需求、缺陷或 Change 相关对话前，选择适合本轮任务的模型和推理强度。
- 开发与项目成员：在简单咨询、代码修改、复杂排查之间切换执行配置，减少误用高成本或不匹配配置。
- 平台运维与产品管理员：通过服务端配置控制可用 Agent、模型与推理选项，避免前端暴露不可用能力。

## 3. 范围

### 3.1 首版包含

- 聊天输入区新增 Agent 选择入口，当前可选项有且只有 Codex。
- 聊天输入区新增模型选择入口，选项由服务端返回的当前可用模型配置驱动。
- 聊天输入区新增推理程序或推理强度选择入口，交互参考 Codex 聊天框的紧凑选择体验。
- 选择结果在新建会话、继续会话和每轮发送时进入执行请求、轮次记录和可追溯展示。
- 当前仅有 Codex 时，Agent 控件仍需表达当前执行主体；可采用只读、禁用下拉或单项下拉，但状态必须清晰。
- 覆盖选项加载、不可用、降级、长模型名、窄屏和发送中禁用等状态。

### 3.2 首版不包含

- 不新增除 Codex 以外的真实 Agent 接入。
- 不新增用户自定义模型、外部模型供应商绑定或个人 API Key 管理。
- 不新增后台 Agent/模型配置管理页面；首版可复用服务端配置、环境配置或既有能力注册表。
- 不改变已有 Chat 工作台的会话权限、空间权限、仓库授权、执行隔离、停止、重试和历史管理规则。
- 不把模型或推理选项作为绕过 OpenSpec、Sprint 或正式开发授权的入口。
- 不新增移动端、微信小程序、桌面端或管理后台界面。

## 4. 功能要求

### FR-001 Agent 选择入口

聊天输入区应展示 Agent 选择入口。首版当前可选项只有 Codex，默认值为 Codex。

当只有一个 Agent 可用时，界面可以展示为只读标签、禁用下拉或单项选择器，但必须让用户明确当前执行主体是 Codex。若后续服务端返回多个 Agent，控件应能扩展为可选择状态，不需要重做输入区布局。

### FR-002 模型选择入口

聊天输入区应展示模型选择入口，默认值来自服务端能力配置或用户/空间可用配置。模型选项不得在前端硬编码为不可验证的固定列表。

模型选项至少应包含面向用户的显示名、稳定值、可用状态和禁用原因。长模型名在桌面与窄屏下不得挤压输入框、发送按钮或执行状态。

首版默认能力配置应与 Codex 当前可选模型保持同步：`GPT-5.6 Sol`、`GPT-6 Astra`、`GPT-5.6 Terra`、`GPT-5.6 Luna`、`GPT-5.5`。前端仍以服务端返回的稳定值和显示名为事实源，不维护独立模型常量。

### FR-003 推理程序或推理强度选择入口

聊天输入区应展示推理程序或推理强度选择入口，用于控制本轮执行的推理配置。命名可在设计阶段收敛为“推理程序”“推理强度”或与 Codex 聊天框一致的产品文案，但底层需映射到稳定配置值。

选项应由服务端返回或由前后端共享配置约束，不得展示执行端不支持的值。不可用选项应有轻量说明，而不是发送后才以未知错误失败。

### FR-004 选择结果进入执行链路

用户发送消息时，当前 Agent、模型和推理配置应随执行请求传入后端，并写入本轮执行记录或等价事实源。

历史消息、轮次详情或执行元信息中应能追溯该轮实际使用的 Agent、模型和推理配置。若服务端因能力限制或降级策略使用了不同配置，页面应展示实际生效值，并保留降级原因摘要。

### FR-005 新建会话与继续会话行为

新建会话时应使用当前默认执行配置。继续已有会话时，页面应明确当前配置对后续新消息生效，不重写历史轮次配置。

若执行端或产品策略要求同一会话固定模型或推理配置，则切换选项时应给出明确限制或引导用户创建新会话；不得让用户以为已切换但实际仍沿用旧配置。

### FR-006 选项加载、失败与降级

页面加载 Chat 工作台时应获取可用 Agent、模型和推理配置。加载中应保持输入区布局稳定；加载失败时可以使用服务端默认配置继续，或禁用发送并展示可恢复提示，具体策略需与实现阶段能力保持一致。

当某个模型或推理配置因权限、额度、执行端版本或服务端策略不可用时，应展示禁用态与简短原因。错误提示不得暴露内部路径、完整配置、密钥、Token、Authorization、Cookie 或 `.env` 内容。

### FR-007 发送中与运行中约束

同会话已有未完成执行时，Agent、模型和推理配置控件应进入不可影响当前运行的状态。用户可以查看当前配置，但不得通过切换控件改变已经发出的执行。

如果允许用户在运行中预设下一轮配置，页面必须清楚区分“当前运行配置”和“下一轮配置”；首版可选择在运行中禁用配置修改以降低歧义。

### FR-008 权限、额度与安全

可用模型与推理配置必须受当前用户、空间、服务端配置和执行端能力约束。无权或不可用的配置不得通过前端隐藏绕过；后端发送接口仍需校验。

模型、推理配置和 Agent 标识可以进入请求摘要、执行记录和脱敏观测 metadata，但不得记录完整 Prompt、完整回复、完整 Diff、密钥、凭证、本机绝对路径或真实客户敏感数据。

### FR-009 测试与文档

后续实现阶段应覆盖 Agent 单项状态、模型选择、推理选择、不可用选项、加载失败、发送参数、历史轮次追溯、运行中禁用、权限拒绝和窄屏布局测试。

如新增或调整 API 字段，应同步 OpenAPI、客户端类型、错误码、API 文档和相关测试。如新增数据持久化字段，应同步数据库设计、迁移和 SQLite/MySQL 兼容测试。

## 5. UI 约束

- 控件应位于聊天输入区附近，优先使用紧凑下拉、菜单或分段式选择，不占用大面积说明文案。
- 当前仅 Codex 时，Agent 状态应清晰但视觉权重低于用户输入框和发送动作。
- 模型和推理选择应支持长文本截断、tooltip 或菜单详情，避免撑破输入区。
- 窄屏下控件可换行或进入更多菜单，但不能遮挡文本输入、发送按钮、停止按钮或执行状态。
- 发送中、停止中、状态未知和已归档会话下的控件状态应与现有 Chat 工作台运行状态一致。
- 选项菜单、禁用说明和错误提示应沿用 Chat 工作台 Ops 风格、设计 Token、深浅主题和近直角组件规则。
