# 用户故事

## US-001 查看当前执行主体

作为 Chat 工作台用户，我希望在聊天输入区看到当前执行主体是 Codex，以便在发送前确认本轮对话由哪个 Agent 执行。

验收要点：

- 当前仅有 Codex 时，Agent 控件展示清晰，不让用户误以为存在其他可选 Agent。
- 控件状态与服务端能力一致；仅一个 Agent 时可只读、禁用下拉或单项下拉。
- 控件不遮挡输入框、发送按钮、停止按钮和执行状态。

## US-002 选择模型

作为产品负责人或开发成员，我希望在发送消息前选择可用模型，以便根据咨询、修改或复杂排查任务选择合适配置。

验收要点：

- 模型列表来自服务端能力配置，包含显示名、稳定值、可用状态和禁用原因。
- 默认模型明确展示，长模型名有截断或 tooltip，不撑破输入区。
- 无权、额度不足或执行端不支持的模型不能通过前端绕过后端校验。

## US-003 选择推理程序或推理强度

作为需要复杂分析的用户，我希望调整推理程序或推理强度，以便在简单问题与复杂研发任务之间使用不同执行策略。

验收要点：

- 推理配置选项有稳定值，并能映射到执行端实际支持的配置。
- 不可用选项有轻量原因说明，不在发送后才暴露未知错误。
- 命名可在设计阶段与 Codex 聊天框对齐，但用户可见文案必须产品化。

## US-004 发送时配置生效

作为用户，我希望发送消息时当前 Agent、模型和推理配置真实进入执行链路，以便选择不是静态装饰。

验收要点：

- 发送 API 携带配置标识，后端重新校验权限和可用性。
- 轮次事实源记录请求配置、实际生效配置和降级原因摘要。
- 服务端降级或拒绝时，页面展示可理解结果，不泄漏内部配置、密钥或路径。

## US-005 查看历史轮次配置

作为排障或复盘用户，我希望在历史轮次中看到实际使用的 Agent、模型和推理配置，以便解释执行效果和后续调整。

验收要点：

- 轮次详情展示实际生效配置，不改写历史轮次。
- 继续会话切换配置只影响后续消息，历史消息保持原配置。
- 若同会话固定配置，切换时明确提示限制或引导新建会话。

## US-006 运行中配置边界

作为正在等待执行结果的用户，我希望运行中配置控件不会改变已经发出的执行，以避免当前运行状态变得不可解释。

验收要点：

- 同会话运行中控件默认禁用或明确标注只影响下一轮。
- 当前运行配置和下一轮预设配置不会混淆。
- 状态未知、停止中和已归档会话下遵守 Chat 工作台既有运行边界。

## US-007 平台治理与观测

作为平台运维或产品管理员，我希望配置选择被安全记录和脱敏观测，以便排查执行效果、能力降级和权限拒绝。

验收要点：

- 行为事件和请求日志只保存脱敏配置标识、结果和错误码。
- Task Trace 记录实际生效配置摘要和降级节点，不保存完整 Prompt、回复或 Diff。
- API、DB、OpenAPI、客户端类型和测试在实现阶段同步。
