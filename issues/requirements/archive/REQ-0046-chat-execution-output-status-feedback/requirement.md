# Chat 按执行状态优化过程输出提示与结果反馈

## 1. 背景与目标

Chat 已将执行过程输出保留在对话中，避免异常结束时轨迹有文字而正文为空。当前通用“部分输出 · 不代表执行完成”提示同时覆盖正常运行和异常情况：运行中与执行状态重复，异常时又不能充分说明失败、停止、未知或正文缺口的差别。

本需求统一消息反馈规则，让用户判断当前是否仍在执行、正文是否完整、业务结果是否通过校验，并获得对应轮次的有效查看入口。保留已有过程输出能力，不以隐藏风险换取界面简洁。

现状依据来自本会话已完成的浏览器刷新观察、BUG-0028 脱敏轮次样本及共用代码：`src/backend/app/chat/assistant_output.py`、`src/web/src/components/chat/ConversationMessages.tsx`。正常完成样本不带部分输出标识，失败样本带标识但未截断；这些是历史观察，不是对全部命令的现场复现。

## 2. 目标用户与价值

- 使用治理命令的产品与研发成员：清楚区分过程叙述、执行终态和业务结果，减少重复操作。
- 普通对话用户：正常交流减少无意义警告，失败或内容缺失时得到具体说明。
- 排障人员：从反馈进入正确轮次轨迹，保留原有权限与脱敏边界。

评审确认优先级 P2，作为现有 Chat 反馈体验优化独立交付。

## 3. 范围

包含所有使用共用 Chat 消息展示的治理命令、Skill 与普通对话；覆盖实时输出、历史消息、刷新和重连，以及执行状态、正文完整性和业务校验的组合。

不包含命令执行状态机调整、会话新建/复用策略、对象互斥、卡片迁移门禁（BUG-0044 范围）；不新增自动重试、自动停止、成果回滚、会话合并或全站通知系统；不重做附件输入、Skill 选择或整体页面布局。

## 4. 功能要求

### FR-001 分离三类事实

分别使用可信执行状态、正文完整性和业务校验结果决定反馈。助手自然语言中的“完成”“成功”不是状态来源。普通对话没有业务校验时视为不适用，不能显示“校验通过”。执行完成不保证正文完整或业务成功；正文完整也不保证执行成功。

### FR-002 正常过程去重

排队、连接、执行和停止请求处理中保持各自真实状态，正常持续输出不重复显示“不代表执行完成”。正文持续可读，不额外将正常流式未结束包装成异常。停止请求处理中不能提前显示“已停止”。

### FR-003 正常完成

执行成功且最终正文完整时清除过程性警告；已有业务校验待定或拒绝信息仍保留。没有最终答复或完整性无法确认时不得伪装成完整成功答复。

### FR-004 失败与停止

失败显示“执行失败”，停止显示“已停止”。有过程正文时补充“已保留过程输出”；没有正文时使用“未收到可展示的输出”，不声称已经保留内容。不再并列重复展示通用部分输出警告。

### FR-005 未知与状态读取异常

服务端轮次未知显示“执行结果待确认”；请求失败或本地加载尚未完成显示“状态暂不可用/正在读取状态”，不得直接改写为服务端未知、失败或成功。提供查看轨迹或已有可用的核对入口，并提醒结果确认前避免重复执行写入命令。刷新状态不能等价为重新发送命令。

### FR-006 正文缺口

区分已知截断/缺口、未收到最终答复、完整性无法确认。已知缺口显示“输出内容不完整”；执行已结束但缺少最终答复显示“未收到最终答复，以下为已保留的过程输出”（无正文时调整措辞）。正常运行尚未到达最终答复不触发此警告。成功、失败或停止状态与正文缺口可共存，不能相互覆盖。

### FR-007 业务结果校验

适用且校验拒绝时显示“结果未通过校验”，提供可安全展示的原因或查看入口；助手正文声称成功时标识为过程内容，沿用可展开查看机制，不能用正文覆盖拒绝事实。校验待定显示“结果待校验”；没有可用校验事实不臆造通过或失败。

### FR-008 每轮统一状态与组合优先级

每轮消息只有一个主状态入口，顺序为状态图标与主状态、必要业务说明、工具调用次数、执行配置、详情展开入口。工具次数显示“5 次工具调用”，不使用“已读”。删除会话底部独立恢复大面板；迁移仅作用于恢复组件，不移除消息列表、正文、输入区或历史阅读能力。

底层分别保存执行终态、业务操作阶段与结果、正文完整性、展示读取状态。前端统一投影，不修改执行器状态机，不从助手正文提取完成结论。

| 主状态 | 可信依据与展示约束 |
|---|---|
| 排队中 | 已接收且尚未执行 |
| 准备中 | 连接或准备环境；详情保留“连接中”等具体步骤 |
| 执行中 | 模型或工具正在工作；工具活动只作为辅助信息 |
| 停止中 | 停止请求处理中，不能提前宣告停止 |
| 校验中 | 后端确认正在校验成果；仅知道待校验时显示“待处理 · 结果待校验”，不能伪造运行进度 |
| 应用中 | 后端确认正在写入与同步，模型结束不提前显示已完成 |
| 确认中 | 已应用，正在回读确认 |
| 待处理 | 阶段受阻、等待用户选择或校验拒绝，展示具体原因；等待输入仅在有可信等待事件及既有回答能力时提供入口 |
| 已完成 | 普通聊天：执行成功；适用业务操作：满足该命令全部完成门禁。正文缺口独立提示，不伪造完整答复 |
| 执行失败 / 已停止 | 保留原执行终态及已有成果情况，不表示成果被回滚 |
| 结果待确认 | 服务端无法确认执行或业务结果；禁止暗示可重复写入 |

投影按以下顺序决策，不把几种事实覆盖成一个底层枚举：

1. 当前读取中或请求失败为展示覆盖层。无可信快照显示“正在读取状态 / 状态暂不可用”；有旧快照可保留并注明“上次确认，更新失败”，不撤销已知完成事实，不使用陈旧权限开放写动作。
2. 同一业务操作已有可信完成证明，主状态为“已完成”。恢复完成追加“经恢复完成”，详情保留原失败/停止终态；与当前操作无关的后续操作成功不能改写本轮。若仍收到矛盾的活动/占用事实，标记结果待确认并重新核验，禁用恢复写入。
3. 无完成证明时，执行未知优先显示结果待确认；停止请求中显示停止中。失败/停止且尚未开始合法恢复时保留原终态，补充可恢复或校验拒绝原因。
4. 合法恢复正在进行时，以实际校验/应用/确认阶段为主状态，注明“恢复中 · 原执行失败/已停止”；其后阻断显示待处理，并保留原终态。
5. 正常执行依次显示排队、准备、执行。模型结束后，业务阶段仍活动则显示实际阶段；阶段阻断/拒绝显示待处理；缺少业务结果显示结果待确认；无业务校验的普通聊天可显示已完成。
6. 已知正文缺口、无最终答复、完整性未知作为同一区域补充信息，去重但不隐藏；正常运行尚无最终答复不警告。更晚可信正文到达只消除已解决提示。

“本次操作已完成”不代表整个 REQ 已交付、验收通过或可归档。其他治理命令使用各自已有的可信完成证明；没有证明时不硬套评审六阶段或推断业务成功。

### FR-009 入口与操作安全

点击主状态行打开当前轮次的统一执行详情，集中提供实际阶段、原执行终态、轨迹、结果证据和恢复动作。结果校验详情复用已有可访问入口；没有入口时仅展示可靠原因。核对/恢复入口仅在能力明确可用且当前用户有权限时出现；不得创建无效按钮或自动提交写操作。重试、停止的原有授权和交互规则保持不变。

### FR-010 全入口与历史一致性

同一状态组合不因命令名称、卡片来源或普通聊天而改变提示语义。覆盖新增消息、流式到终态、历史分页、刷新、重连、无正文和旧消息字段缺失。旧字段缺失时不推断内容完整、校验通过或执行成功；也不因缺少新字段给所有历史消息增加误报警告，使用已有可靠状态并标注无法确认的必要事实。

## 5. UI 与可访问性约束

复用当前 Chat 消息组件、执行状态行、正文和轨迹布局；不进行附件截图的一对一视觉复刻。之前截图用于现象说明，不作为视觉稿。

提示使用中文业务文案，不展示内部事件类型、字段名或堆栈。状态不只依赖颜色，异常说明和动作支持键盘访问；实时状态更新不逐 token 重复播报。长原因可折叠，保留阅读正文与复制功能，不使窄屏布局溢出。

后续验收采集 1440px 与关键窄视口下运行中、失败/未知、正文缺口、校验拒绝及展开轨迹的证据；正式 selector、样式采样和交互验证在需求完善/Change 阶段定义。req-complete 已补充局部模拟原型及 context.md，原型不代表产品实现。

## 7. 验证要求与成功标准

建立三维状态组合测试，至少覆盖 FR-008 的组合、无正文、最终答复迟到、请求错误、字段缺失及校验不适用。正常运行不重复警告；失败/停止/未知明确；成功但正文缺口或校验拒绝不被掩盖。

组件/接口合成回归与真实浏览器观察分别记录；后者验证实时到终态、刷新重连、历史阅读和正确轮次轨迹。覆盖治理命令与普通对话代表样本，并通过入口映射确认共用规则；不声称每个命令都已真实执行。具体验收编号在 req-complete 中形成。

### FR-011 轮次归属与详情收敛

消息以 conversation_id + turn_id 关联 operation_id；一个操作包含多个执行/恢复尝试时保留明确关联，不能按对象 ID 或会话最新 candidate 推断归属。旧轮次缺少可靠关联只展示可证明的执行事实并注明业务结果未关联；不挂接最新成功成果。

详情展示准备、生成、校验、应用、回读、完成中实际适用的阶段；明确已完成、当前、阻断、未开始与不适用，非线性恢复也按事实展示。正常完成默认折叠；异常原因和必要动作在本轮就地可见，长原因展开。恢复预算、次数、截止时间仅在适用的恢复详情出现，成功态不常驻显示。恢复成功在原轮次状态中追加结构化确认，不改写助手原文或历史终态。

### FR-012 恢复动作族

| 动作 | 可用条件 | 交互与结果 |
|---|---|---|
| 查看详情/轨迹 | 对应轮次可读 | 打开同一详情区域，关闭/再次点击返回；不触发写入 |
| 刷新状态 | 有读取权限 | 只读核验，保留上下文，不重发命令；按钮只在读取失败/待确认或详情内出现 |
| 查看证据 | 后端允许 evidence | 从本轮详情打开脱敏证据弹窗，包含操作、成果、应用与版本关联 |
| 继续剩余步骤 | 后端允许 resume、当前权限与版本有效 | 确认弹窗说明对象、阶段、复用成果、不重跑模型；提交防重复，版本变化须重新确认；成功提交只显示等待核验，不提前完成 |
| 重新生成草稿 | 后端允许 regenerate | 将命令放入当前会话草稿；已有非空草稿先确认替换或取消；明确发送后才执行，生成新操作并保留来源 |
| 停止/重试原轮次 | 原有能力明确可用 | 复用原有授权与确认规则，不以通用重试替代安全续接；状态未知不开放重试写入 |

只读、无权限、过期、成果变更、预算耗尽、重复请求与恢复失败均显示具体原因及仍可用的查看入口。服务端再次核验权限、版本和幂等性；前端隐藏按钮不替代安全校验。既有停止/重试仍由执行详情承载，不新增执行能力。

## 10. 生命周期与执行保护一致性展示补充

### FR-013 卡片阶段与执行异常分层

需求中心与 Chat 使用同一可信操作结果。生命周期已核验为 approved 时，卡片保留“已评审”列并叠加“执行结果待核对”，不能因旧执行保护回退至待评审。生命周期来自可信核验，不只读取任一文件字符串；生命周期尚不可信时明确标注未确认。下一步动作是否开放独立受后端准入控制，已评审不表示可以绕过保护加入迭代。

历史操作完成、当前资源版本变化与下一步可执行性分别解释。Chat 完成与卡片待核对并存时展示原因、所属操作和最近核验时间，不互相覆盖、不要求重复评审。所有展示缺失字段回退至“状态暂不可用/结果待确认”，不猜测原因。

### FR-014 核验原因与入口

统一原因文案：完成证明缺失、相关文件已变化、执行占用待确认、当前无权限、状态读取失败；详情可显示安全的差异摘要与最近核验结果，不泄漏内部堆栈或凭证。恢复写入失败与只读核验失败分别表达。

| 入口 | 能力条件 | 交互规则 |
|---|---|---|
| 重新核验 | 后端明确允许核验 | 核对既有结果，不重新执行模型或应用成果；处理中去重，完成后刷新 Chat 与卡片的共享投影，失败保留旧事实并解释 |
| 查看差异 | 已授权且存在可读差异 | 只读详情/弹窗，指出相关对象与依赖变化，支持关闭/Esc；无数据时说明暂无可用差异，不造按钮 |
| 查看原执行 | 可访问原会话/轮次 | 定位对应操作，不跳到会话最新轮次；无权限给出解释 |

后台安全核对由 BUG 链路负责；前端不无限轮询或重复提醒，只在结果变化或需要用户处理时提示。未提供核验能力时保留原因和已可用的查看入口，不显示虚假可操作控件。
