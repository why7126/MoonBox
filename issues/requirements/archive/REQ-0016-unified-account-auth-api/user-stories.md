# 用户故事

## US-001 统一登录进入工作台

作为前台需求中心用户，我希望通过统一 `/login` 入口登录 MoonBox，并由系统调用 `/api/v1/auth/login` 建立登录态，以便不再关心前台和后台是否使用不同认证接口。

验收要点：

- 登录成功后返回 access token、过期时间和当前用户摘要。
- 前端只写入统一 session，不再同时维护前台和后台两套 session。
- 普通前台用户可进入需求中心；后台管理员可在具备权限时进入后台。
- 旧 `/api/v1/admin/auth/login` 不再可用。

## US-002 当前用户维护个人资料

作为任意已登录用户，我希望在前台或后台个人资料入口维护自己的昵称和头像，以便前后台当前用户展示保持一致。

验收要点：

- `GET /api/v1/auth/me` 可读取当前用户摘要，不要求后台管理员角色。
- `PATCH /api/v1/auth/me` 只允许修改当前用户自己的昵称和头像 URL。
- 昵称允许清空，最长 128 个字符，清空后前端回退展示用户名。
- 保存成功后前台需求中心、后台用户菜单和统一 session 同步刷新。

## US-003 当前用户上传头像

作为任意已登录用户，我希望通过统一认证域上传头像，并在同一会话立即看到头像回显，以便个人资料更新流程完整可用。

验收要点：

- 头像上传使用 `/api/v1/auth/avatar` 或等价统一认证路径。
- 支持 JPG、PNG、WebP，单文件不超过 2MB。
- 上传具备 `idle -> uploading -> done/failed` 状态机。
- 上传成功返回持久头像 URL，前端不得保存 `blob:` URL 到用户资料。
- Docker 本地 `:3000` 环境可完成上传、读取和回显。

## US-004 当前用户自助修改密码

作为任意已登录用户，我希望通过统一认证域修改自己的密码，以便前台用户和后台管理员使用一致的账号安全能力。

验收要点：

- 修改密码使用 `/api/v1/auth/change-password`。
- 请求包含当前密码、新密码和确认新密码。
- 修改成功后撤销该用户所有服务端会话。
- 前端清理统一 session 并引导用户重新登录。

## US-005 后台权限不被统一认证削弱

作为安全审计相关角色，我希望统一认证只解决登录态和个人中心问题，后台资源仍保持独立授权，以便普通前台用户无法访问管理后台敏感接口。

验收要点：

- `/api/v1/admin/**` 继续要求后台管理员角色或等价权限。
- 普通前台用户可登录、改资料、改密码、上传头像，但不得调用后台用户管理接口。
- 前端 `can_access_admin` 仅用于展示入口，后端不得信任前端权限字段。

## US-006 破坏性路径迁移可验证

作为研发团队，我希望旧 `/api/v1/admin/auth/*` 路径从代码、测试和文档中清理，以便后续不会继续误用后台命名作为统一认证入口。

验收要点：

- 后端不再注册旧 `/api/v1/admin/auth/*`。
- 前端调用、测试、OpenAPI、客户端生成物和 API 文档均只引用 `/api/v1/auth/*`。
- 发布或验收材料明确旧路径不可用。
