# 继承迭代操作权限的工作区成果确认合入

## 1. 背景与问题

多 worktree 成果需要进入同一主线，单纯显示开发完成或仅凭 Agent 声明不足以证明可以交付。用户最终选择验收和候选合并验证通过后，由具有所属迭代操作权限的人确认，替换此前自动合入提议；系统随后完成受控合入与记录续接。

## 2. 目标用户与业务目标

具有迭代操作权限的成员需要审阅本次成果并确认；开发者需要知道冲突、过期验证和权限原因；维护者需要在 Git 与数据库之间中断时恢复真实交付事实。目标是权限继承清晰、确认绑定版本、主线受保护、结果可追溯。

## 3. 范围与非目标

纳入 Sprint 归属与操作权限解析、提交固定、候选合并、组合验证、人工确认、串行集成、主看板更新、幂等和故障恢复。

不纳入自动合入、额外审批人名单、强制双人审批、自动变基/压缩提交、远端推送、发布、替代正式归档或重建验收环境供应。

## 4. 功能要求

### FR-001 交付与迭代归属

服务端从受管理工作树解析交付链路、具体交付 Change 和所属 Sprint，核对正式纳入事实与当前状态。REQ/BUG 子 Change 串行复用工作树，但每次候选限定明确交付范围。迭代归属缺失、多义、跨迭代混合成果或关联变化不能猜测授权，先阻断并修复范围。

### FR-002 迭代操作权限继承

确认合入默认复用所属迭代的有效操作权限，不把查看权限当操作权限，不仅凭创建者、执行者或角色名授权。有效空间/仓库/对象访问与迭代操作权限同时满足；其他迭代权限不外溢。允许具有同等权限的发起者自确认，不要求独立第二人。实际复用现有授权事实源，若缺独立能力则先建立共用解析入口，不虚构已存在的权限表。

### FR-003 版本固定与范围校验

固定来源提交、目标分支及提交、交付范围和验证输入指纹；未提交成果先明确处置，不自动包含无关文件。保留来源提交历史，首期不自动变基或 squash。目标为明确配置的本地主线，不能根据界面默认分支猜测。

### FR-004 候选合并及组合验证

工作区验收通过后，在临时集成工作树准备候选，检查代码、治理文档、生成物和适用测试。证据绑定来源、目标、候选提交/树及环境；来源单独通过不代替组合通过。冲突保留源成果并回到原开发工作区处理，临时树受生命周期管理。复用 REQ-0048 供应和既有验收计划，不重新建设验收执行系统。

### FR-005 人工确认与版本失效

确认页面呈现精确差异、验证结果和影响。请求携带候选版本及幂等标识，服务端保存确认人、时间、授权依据与证据关联。确认不永久授权工作树。来源/目标/候选变化需重新验证并再次确认；权限撤销或迭代关联变化使未执行授权失效。即使修改后内容看似相同，也按候选身份核对，不能无依据继承旧确认。

### FR-006 合入队列与执行复核

同仓库集成串行领取，执行时重查确认有效性、身份权限、目标版本、恢复引用和主目录状态。主目录有可能被覆盖的人工修改则阻断，不自动 stash、强制 reset 或覆盖。验证失败、权限不足和文件冲突分别报告。确认完成后由可信服务执行，不要求用户手工 Git 操作。

### FR-007 持久操作与失败恢复

Git 和数据库不假定原子事务。操作持久记录身份、来源/目标/候选、授权、执行代次、步骤和实际结果；幂等防重复点击/回调。Git 已成功而 DB 回写失败时核对提交再补记，不再次合并或重置。结果未知保留锁/保护依据，恢复服务只在证据充足时推进；部分治理投影更新失败可以续接，不重跑已完成合并。

### FR-008 主线治理与归档分离

任务工作树的实现及限定文档合入后，由主线受控流程更新共用注册表和 Sprint 汇总，保留事实回读。开发完成、验收通过、已合入、正式归档分别记录；正式规格仍经归档生效。不可把任务分支随意改写的共享状态直接视为正式治理结果。合入后不自动归档、推送或发布。

### FR-009 结果和工作区保留

合并记录保存实际提交、验证和授权证据，保护所需恢复点；完成后工作树可供检查和返修，清理须符合 REQ-0042/0054，无活动写入、未提交/未合入成果和未解决恢复依赖。已合入成果撤销走受控新变更，不用旧快照覆盖主目录。

### FR-010 状态与操作能力

展示待验证、冲突/返修、待确认、排队合入、合入中、已合入、待恢复等阶段；状态与事件有真实依据。服务端返回可否确认及稳定原因，迭代仅可查看时提示需要所属迭代操作权限，有权限但验证失败展示具体门禁。刷新和断线不制造重复请求。

### FR-011 模块边界和审计

moonbox-app-server 完成请求及权限入口，moonbox-core 协调合并业务与有效状态，moonbox-worktree 管候选目录和可信 Git 操作，moonbox-exec-server 执行受限检查，moonbox-rollout 关联操作历史与恢复证据，moonbox-ui 展示审阅和确认。授权审计记录不可被通用遥测替代；遥测失败不改变已完成的合入事实。

## 5. UI 约束

在工作区/交付详情展示本次来源、目标、范围、差异和验证摘要；提供查看差异、确认合入、返回返修、查看恢复状态等适用动作，不新增独立审批人配置页面。确认按钮以服务端能力为准，过期候选显示重新验证和确认提示。确认执行状态与真实合入结果分开。动作族及弹窗状态见 business-flow.md 和 prototype/web/context.md，首期不新增 TUI。

## 6. 数据、安全与部署影响

涉及 Web、API、数据库、Agent 执行与安全边界；实施时同步 OpenAPI、Orval 客户端、数据库设计、SQLite/MySQL 兼容迁移、部署挂载与权限规则和测试。只迁移本需求关联数据，不修写无关历史事实。路径、密钥、完整 Prompt 和文件正文不进入通用观测日志。业务证据按授权存储，路径不作为客户端权限依据。

## 10. 细化方案与实现风险

### 迭代操作资格与既有实现映射

当前静态依据：`src/backend/app/governance/scope.py` 的 `authorize(write=True)` 使用有效空间、所有者或管理员/编辑者、仓库绑定；`visible` 与 `chat_object_access.can_read` 表达对象可见性；`src/backend/app/chat/policy.py` 还施加命令和治理阶段限制，不能把某次 `write_allowed` 布尔值直接当永久合入权。未发现独立 Sprint 写权限字段，本需求不宣称已有此权限表。

首期共用“迭代操作能力”解析：有效可写空间与仓库 + 当前 Sprint/链路/Change/工作区访问 + 唯一正式 Sprint 归属 + 操作类型所需门禁。合入默认继承该能力，不增设审批名单；已有其他对象限制继续取交集。能力接口的最终名称在 Change 定义，前端不能硬编码角色名单。

| 迭代状态 | 首期合入资格 |
|---|---|
| planning / active / in_progress | 正式纳入且验收和候选验证通过后可进入确认；planning 不因尚未启动额外阻断 |
| completed / closed / archived | 只读追溯，拒绝新候选及未执行合入；保留旧证据 |
| 缺失、重复、无法解析、取消或未知状态 | 阻断并说明归属/状态不可确认 |

关闭迭代中的遗留成果经现有治理流程明确重新纳入有效迭代后才重建候选、复验和确认；不自动改迭代、重新打开迭代或沿用旧授权。关闭/撤权发生在队列等待期间时执行前拒绝；若 Git 已完成仅做事实对账，不通过回滚来抹去已完成结果。上述为本次需求细化的首期规则，已通过本次需求评审。

具体接口、数据库字段、物理模块路径与部署并发参数在正式评审和 Sprint 纳入后的 Change 设计确定；不阻碍需求文档评审。
