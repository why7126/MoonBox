# 本地项目绑定与 Chat、需求中心迭代闭环

## 1. 背景与来源

原始记录希望将本地存量项目导入 MoonBox，并在产品内完成需求治理、Codex 执行、验收和归档。2026-09-11 探索进一步收敛目标：Chat 工作台已经接入本地 MoonBox 仓库，希望需求中心绑定同一项目并自动更新，先以一个真实本地项目验证 MVP。

当前代码具备以下基础，但不代表本需求已经实现：

- 需求中心从全局治理目录读取 REQ、BUG、Sprint 和 OpenSpec；页面加载及手动刷新重新读取，空间选择尚未形成仓库级查询绑定。
- Chat 已有空间、仓库和治理目录绑定；执行工作区从源仓库已提交树初始化，会话修改保留在独立副本中。原仓库未提交内容不会自动进入副本，副本修改不会自动回写原仓库。
- 单机 Compose 已配置治理文件目录挂载，但实际部署的目录对应关系仍需在实施和验收时核对。

本 PRD 承接探索推荐，将“单项目绑定、自动刷新、Chat 成果受控应用”作为已评审范围；成果应用仍逐次要求用户确认，不代表允许自动写回或绕过 Sprint/OpenSpec 直接开发。

代码依据：`src/backend/app/services/requirement_center.py`、`src/backend/app/chat/settings.py`、`src/backend/app/chat/workspace.py`、`src/backend/app/chat/platform_worker.py`、`src/web/src/pages/catalog/RequirementCenterPage.tsx`、`docker-compose.yml`。

## 2. 目标用户与价值

面向使用本地仓库和 MoonBox 治理规范的 AI 创业者、小型研发团队及 MoonBox 自身产品团队。用户能够围绕同一个需求，在需求中心查看最新事实、进入关联 Chat 执行治理工作、审阅并应用结果，返回看板观察真实更新，减少手工复制命令、切换目录和核对状态。

MVP 成功标准：一个真实 MoonBox 项目完成“需求卡 → 关联 Chat → 治理文档变更 → 差异确认 → 应用到项目 → 看板和文档自动更新”，以真实执行和文件证据验收。

## 3. 范围

### 3.1 首版包含

- 一个预配置、授权的 MoonBox 本地验证项目；本地指执行服务可访问的仓库，不承诺浏览器直接读取用户电脑任意路径。
- Chat 与需求中心共用项目身份、仓库绑定、治理事实源及权限范围。
- REQ/BUG 卡片、文档、关联 Change 和 Sprint 进度按项目读取并自动更新。
- 从需求卡发起或继续本人关联 Chat，执行一个合法的治理动作并保留真实 Diff。
- 治理文档成果的预览、显式确认应用、版本冲突阻断、失败恢复和刷新反馈。
- 单项目写入串行化、状态真实性、基础审计与真实端到端验收。

### 3.2 首版不包含

- 任意本地目录自助导入、远程 Git 克隆平台、多仓库统一管理、跨设备同步。
- 全部生命周期动作按钮一次性交付，或全自动评审、Sprint 纳入、合并、归档、发布。
- 通用业务代码成果合并、自动提交或推送；本期应用范围限定为所选治理动作的受控文档变更。
- 多会话同时写入同一项目、无提示覆盖冲突、绕过权限或治理状态门禁。
- 重建 Chat 执行器、凭证体系、备份机制或现有需求中心视觉系统。

## 4. 产品流程与事实源

用户进入已授权的 MoonBox 项目 → 需求中心读取项目原仓库治理事实 → 从卡片打开关联 Chat → 校验动作与上下文版本 → 在独立工作区执行 → 展示待应用成果 → 用户确认差异 → 再次校验目标版本并应用 → 校验治理文档一致性 → 看板与文档刷新。

原仓库是项目正式治理事实源；会话副本是执行成果工作区，历史轮次快照是历史记录。三者身份和版本不能混用。Chat 成功完成一轮只表示执行完成，不表示成果已应用、需求已交付或验收已通过。

## 5. 功能要求

### FR-001 共用项目绑定

服务端维护可复用的空间、项目、仓库与治理目录映射，优先复用已有 Chat 仓库配置，避免两套独立目录配置漂移。两个页面显示一致项目名称与连接状态；未绑定或目录不可用时显示原因，不回退到其他项目或示例数据。客户端只提交受控标识，不能指定文件系统绝对路径。

### FR-002 按项目读取与授权

看板、统计、筛选选项、文档读取和写入均按当前项目解析；服务端检查空间成员、仓库和对象权限。切换项目后清理旧项目内容，迟到响应不得覆盖新项目。首版仅一个验证项目，也不能将全局文件内容返回给其他无权空间。Chat 会话继续保持本人所有权边界。

### FR-003 治理文件聚合

沿用 registry、trace、关联 Change 和 Sprint 的现有派生规则，保留完整对象身份与生命周期目录解析。新建、修改、迁移及归档后刷新卡片、文档入口、状态和任务进度；不把目录名或聊天文字当作唯一状态依据。文件解析失败或一次操作尚未写完时保留最后一次完整可用结果并提示待同步，不能将部分结果显示为完整成功。

### FR-004 自动更新与新鲜度

首版采用轻量轮询，建议间隔 3–5 秒，并在页面恢复可见、重新获得焦点及成果应用完成后触发刷新。在本地服务正常、页面可见且没有未完成写入的条件下，稳定落盘的治理变更在 5 秒内呈现；该指标以本地真实验证为准。后台页面暂停或降低刷新频率，失败采用退避并保留手动重试。

显示最后成功同步时间和同步中、已同步、失败等状态。正在编辑的文档不得被刷新覆盖；检测到外部版本变化时保留草稿并提示比较或重新加载。刷新不重置用户筛选、滚动位置或已选择对象。

### FR-005 需求卡进入 Chat

需求卡提供关联 Chat 入口，携带项目、仓库、完整 REQ/BUG 身份和允许执行的动作意图；用户可以创建新会话或继续本人兼容会话。项目或仓库不匹配的会话不可复用。进入 Chat 不自动发送消息、不触发写入；后续输入按现有 Chat 规则建立本轮上下文快照。

### FR-006 执行上下文与工作区版本

发送前核对所选治理对象在原仓库、引用快照和执行副本中的版本，明确展示版本不一致。原仓库未提交的治理修改不能被静默忽略后继续产生可应用成果。首版可提示用户先完成受控基准准备，再初始化或刷新干净执行副本；不能覆盖已有会话成果，也不能静默改为直接在原仓库执行。具体基准准备方式在 Change 设计中确定并验证。

### FR-007 待应用成果与差异预览

执行结束后，以可信文件差异形成待应用成果，关联项目、对象、会话、轮次、基准及目标版本。区分本轮与累计成果，展示新增、修改、删除和目录迁移的实际影响。只有所选治理动作要求的文档及必要 registry、trace、索引联动文件可以进入应用集合；越界业务代码、凭证、运行数据及不支持的文件类型阻止应用并说明原因。

首条验收链路采用专用 captured 验证需求的 req-generate：生成 PRD 并联动 trace、registry 和索引。失败或停止轮次保留差异，但首版不将其作为完整成功成果应用。

已生效规格不能通过普通文档应用入口直接修改。未处理成果不能因切换页面、刷新或重启而被误标为已应用。

### FR-008 受控应用与冲突保护

用户查看完整文件集合和差异后显式确认应用。服务端重新校验权限、动作门禁、源文件版本和成果版本；采用文件内容基准检查，不能只比较 Git HEAD 而漏掉未提交修改。任何待覆盖文件在执行后被修改时阻止整批应用，保留原文件和成果，提示重新基于最新版本处理，不自动强制覆盖。

批量文档应用要有一致性保护和可恢复结果；中途失败不能留下被宣称为成功的半套治理状态。重复点击或请求重发不重复应用。应用完成后校验关联元数据、文件路径与派生索引，再返回完成状态；失败或状态未知时提供可核对的结果并禁止重复写入，恢复不得撤销其他人的后续修改。

### FR-009 写入协调与治理门禁

首版同一项目的受控写入串行执行，需求中心文档保存和成果应用参与同一协调边界；外部编辑通过版本检查兜底。Chat 执行沿用现有串行和隔离规则。未评审需求不能执行开发，评审后先纳入 Sprint 再转 OpenSpec；应用文件不构成绕过这些门禁的入口。人工只读文档的系统更新仍需经过合法治理动作。

### FR-010 结果回流与恢复

分别展示执行中、执行失败、待应用、应用中、冲突、应用失败、已应用等状态。状态来自可信执行和文件操作结果，不由模型回复推断。应用后刷新当前看板、文档和关联状态；同一会话再次执行前重新检查基准。服务重启后能够恢复成果和应用结果，禁止丢失互斥状态后盲目重试写入。

## 6. UI 约束

沿用当前 Chat、需求中心和共享侧边栏的设计 token、主题及组件。新增内容集中在项目连接状态、卡片 Chat 入口、同步反馈、成果预览与应用确认，不另造项目管理工作台。相关动作、弹窗、状态及选择器在后续设计阶段统一建立矩阵，覆盖加载、空态、错误、冲突、只读和完成状态。

自动同步不能打断输入或弹出连续提示；“执行完成”和“已应用到项目”在视觉和文案上清楚区分。真实数据模式不使用演示数据或模拟进度。后续完成 1440px 及关键窄屏、主题、关键交互视觉验收和 computed style 证据。需求完善阶段提供局部流程原型与拆解，不宣称完成产品视觉验收。

## 7. 权限、部署与数据观测

依据 [产品数据采集与链路观测标准](../../../../docs/standards/product-data-collection-observability.md)，适用声明与验收如下。

目录映射仅在服务端保存，校验越界路径、符号链接和授权范围；API、页面和通用日志不暴露主机路径或凭证。受控应用需要写入治理目录，但不向普通 API 或执行容器扩大任意主机文件写权限；现有只读挂载与新写入通道的关系在设计阶段明确，不以整仓库可写挂载替代权限设计。

```yaml
product_data_collection_observability:
  status: applicable
  affected_layers:
    - web
    - api
    - request_logs
    - usage_events
    - task_traces
    - task_trace_spans
    - agent_workflow
    - deployment
  reason: 项目绑定查询、关联会话及成果应用新增跨页面请求和可恢复写入链路，需要记录真实结果与脱敏版本证据。
  validation: 待实施验证项目授权、请求关联、应用幂等、冲突及失败恢复；本次完成需求验收设计，未运行产品验收。
```

用户点击与后台轮询分别归因，轮询不伪造用户行为事件。应用过程可追溯到项目、对象、会话、轮次、操作者、版本摘要、请求和任务结果；不将文档正文、原始聊天、完整 Diff、绝对路径或认证信息复制到通用观测数据。业务成果按受控权限存储并沿用可适用的保留规则。

DB 是否新增绑定或应用记录结构由设计决定；如新增需同步 SQLite/MySQL 兼容、迁移及测试。对象存储本期不新增依赖，沿用 Chat 现有机制。API、客户端生成、UI、部署和安全文档在实施阶段按实际契约同步。

## 8. MVP 验收要点

1. 已授权账号在两个页面看到同一 MoonBox 项目，其他空间无法读取该项目卡片或文档。
2. 本地修改并稳定保存治理文件后，看板在约定时间内自动更新；原有编辑草稿不丢失。
3. 一个真实需求从卡片进入关联 Chat，完成合法治理动作，展示真实文件差异；未应用前正式看板不提前推进状态。
4. 用户确认应用后原仓库文档、trace 和相关索引一致，看板及文档自动呈现结果。
5. 注入外部编辑冲突、重复提交、应用中断和目录不可用时，原文件不被错误覆盖，结果可恢复且不假报成功。
6. 验收明确源仓库与会话副本基准，包含未提交修改场景；真实浏览器、API、worker 和文件观测证据与合成回归分开记录。

## 实施一致性记录（2026-09-11）

实施接口按空间与仓库显式查询；首版只有 captured REQ 的 req-generate 可准备受控会话。需求中心不展示独立项目连接栏，保留授权项目绑定和工具栏刷新；同步时间在刷新按钮提示中呈现。Chat 在现有关联栏显示项目标识与连接状态。其他阶段动作在真实页面明确提示暂未支持，不以模拟流转替代正式事实。


## 完整仓库看板验收补充

对象总数按 registry 计数，不自动加入未注册基础建设目录。Issue done/archived 不被旧 Change 状态覆盖；Change 与 Sprint 同时支持活动和归档目录。验收态 未归档映射验收中，进行态 映射研发中。验收缺项检查读取真实 Issue/Change 文件，不能使用精简卡片文档列表；历史漂移独立提示，不把已完成项统计为当前阻塞。


## 首屏加载返修

首次加载在指标数字、阶段数量和卡片区域显示原位骨架，不显示0/00或暂无数据，不插入独立加载面板；保持标题、工具栏、阶段列位置。已加载后的手动刷新和轮询继续保留数据、筛选与草稿。

## trace 单入口规则

所有REQ/BUG卡片在所有阶段仅保留一个trace.md入口，读取所属Issue目录的trace.md，标签和标题使用普通文件名；缺失时提示不可用，不回退Change trace。Change trace仍参与内部阶段判断，其他文档入口不变。


### 任务进度文档入口

卡片研发、测试、人工验收入口统一打开关联 tasks.md 的完整 Markdown 文档。加载完成后优先定位匹配章节，其次定位匹配任务并高亮、聚焦；不打开独立进度面板。缺少关联时提示未关联 tasks.md；文件不存在或已移动时提示读取目标缺失；章节或任务缺失时保留完整文档并提示未找到目标，不以计数、历史返修记录或其他文档伪造目标。普通 tasks.md 链接从顶部打开，既有编辑与勾选权限不变。


### Sprint 文档归属

卡片 sprint.md 属于关联 Sprint，通过现有 Issue 文档读取接口按当前授权项目解析。展示、读取和缺失校验共用解析：按关联 ID 查活动目录，仅活动目录不存在时查同 ID 归档目录；活动目录缺文件不读取归档旧副本，不回退 Issue、Change 或其他 Sprint。文件缺失时保留明确提示；读取保持只读，trace.md 仍仅属于当前 REQ/BUG。


### 主动作阻塞与消息避让返修

卡片主动作统一使用接口disabled_reason、Issue阻塞和前置文档缺失判断，阻塞提示、按钮原生禁用、title原因与执行前守卫一致；文档仍可阅读，补齐后刷新恢复按钮。Tips位于Agent助手上方并保留安全间距，提高层级；窄屏限制宽度、长词换行，超长消息在受限高度内滚动，不遮挡助手。


### 主文档持续展示返修

REQ的requirement.md、BUG的bug.md一旦在所属Issue中生成，即在全部阶段卡片持续显示并固定文档列表首位，包括迭代规划、开发、验收和已完成。读取始终来自所属REQ/BUG当前目录，兼容Issue归档迁移；不读取Change同名文档。未生成不伪造入口，文件删除后按最新快照移除，已打开入口读取缺失明确提示。仅调整展示与排序，保留既有阶段编辑和只读权限。


### Sprint 文档持续展示

sprint.md在关联Sprint文档出现后于所有阶段卡片持续展示，包括准备开发态、研发中、验收中和已完成；requirement.md/bug.md仍保持首位。复用关联Sprint读取、只读能力、活动/归档解析及缺失不回退。只扩大展示白名单，不将sprint.md新增为其他阶段的必需文档，不改变阻塞与权限判断。


### 卡片文档分组与排序

常驻区按所属requirement.md/bug.md、关联sprint.md、所属trace.md固定排序；阶段区按当前任务优先排序。准备开发态proposal/spec/design/tasks；研发和验收tasks/spec/design/proposal；已完成archive/tasks/spec/design/proposal；已评审review优先，其他沿阶段阅读顺序。两个分组之间仅保留4px间距，无分隔线与额外内边距，组内自然换行，单组无空白占位；来源、权限及原必需文档校验不变。


### 文档读取与刷新性能

单次Change文档请求复用同一授权稳定快照的临时目录，避免授权和正文读取重复物化；不引入跨请求缓存，保留项目授权、写入恢复、epoch及绑定版本检查。相同项目的context刷新复用进行中请求，初始加载完成后开始轮询；切换项目及卸载取消旧请求。文档内容/草稿/版本冲突处理与原型布局不变。分段日志仅含服务端request_id、操作名、成功状态及各阶段毫秒耗时，不含文档内容或本机路径。


### 卡片更新时间格式

所有阶段REQ/BUG卡片统一显示“更新 YY/MM/DD HH:mm”，保留真实日期及源时间时分，各字段补零；缺失、无效或仅有日期/时分时显示“更新时间未知”，不补造日期和时间。footer必要时换行，时间自身不拆分，避免窄屏挤压动作。


### 所属需求原型常驻入口

所属REQ的prototype.html及prototype目录内HTML存在时，在主文档后常驻展示；多端以相对路径区分，兼容活动/归档目录。发现与读取共用安全解析，缺失无占位、不回退其他Issue/Change、不扩大必需文档校验。维持项目授权、只读预览和4px紧凑分组。


原型入口标签仅显示区分多端所需相对路径（如web/prototype.html、admin/prototype.html），移除“原型 · ”前缀；常驻位置、排序、URL与预览权限不变。
