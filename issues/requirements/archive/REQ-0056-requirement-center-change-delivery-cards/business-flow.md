# 需求中心交付阶段按 Change 独立成卡业务流程

## 主流程

```text
进入已授权项目 → 取得一致快照 → 解析 Issue/Change/归属 → 权限过滤
  ├─ 前期或无有效 Change → Issue 卡/待核实入口
  └─ 有效 Change → 按项目+Change ID 去重 → 自身阶段与 Sprint → 交付卡
       ├─ 来源入口 → 需求整体状态、未交付范围、历史交付
       ├─ 查看进度 → 当前 Change tasks.md → 版本及权限校验 → 原目标写回
       ├─ 查看验收 → 当前 Change 证据 → 来源需求整体验收另行查看
       └─ 阶段动作 → 确认项目/来源/目标 → 能力与权限校验 → 会话预填
                       → 用户执行 → 请求/任务绑定 → 原目标结果与刷新
```

## 决策规则（评审稿）

1. 有合法可解析 Change 后，交付区域不重复输出 Issue 聚合卡；前期工作与后期交付不是对同一对象机械复制。仅异常关联时保留有权限的 Issue 待核实入口。
2. 剩余范围留在来源详情的“未交付范围”区，不新增虚构 Change、不自动重开旧交付；规划入口仍走既有命令门禁。
3. 多来源卡的来源按完整 ID 排序；只读查看不强制选择。执行若需要唯一来源，先选择，不默认首项。来源选择改变时清空旧预填，重新核对目标。
4. 会话可复用，但每次动作上下文含项目、完整来源及目标 Change；能力尚不支持显式目标则阻止执行，不伪造 CLI 参数。设计阶段决定兼容承载方式。
5. 独立估算缺失显示“人力待估算”，Sprint 容量仍读取既有事实源；不按卡片求和重算。

## 异常与恢复

- 无权访问：依原权限隐藏/拒绝；不展示不可见来源名称及数量，不借“独立卡”绕过授权。
- 快照失败：保留明确旧数据标识或错误态，不把旧结果作为最新可执行准入。
- 目标缺失、关系冲突、阶段变化：保留诊断，禁止回退兄弟 Change；刷新后重新确认。
- 并发改任务：版本冲突不覆盖，刷新原 Change 后重试。
- 会话恢复：重验项目、目标、来源关系、权限与阶段；上下文不足要求重选，不能自动继续兄弟交付。
- 历史归档：保持只读与原 Sprint，父需求当前 iteration 不反写历史。

## 与父需求差异

REQ-0026 已覆盖无来源 Change，并让关联 Change 留在 Issue 卡内。本需求让所有有效交付统一按 Change 成卡；保留既有权限、独立 Change、文档读取和阶段执行能力边界。需求整体状态继续由原 Issue 事实源维护。

## 数据与执行边界

原型数据为本地合成样本，不发请求、不写任务、不创建会话；正式页面需要后端返回可信关系、阶段、权限、验收与估算来源。读写与执行以服务端校验为准，不将 UI 参数当成授权。

## 实施口径（2026-10-31）

交付卡保留既有视觉层级，中文交付标题下显示完整 Change ID，随后为元信息标签行。开发、返修和归档先确认项目、Change及唯一来源，再进入绑定此 Change 的 Chat 预填完整来源命令；多来源需选择。自动验收按钮因当前产品执行器没有相应明确目标入口而禁用，CLI 验收流程仍可使用。服务端在发送、执行权限、重试与工作区准备时核对持久绑定、权限和阶段，不猜测兄弟 Change。

同一来源关联多个交付时仅按来源身份统计一次；未知独立估算显示“人力待估算”。来源整体状态、验收与交付自身证据分开。390px 下保留横向看板，单列适配可用宽度，长身份换行；桌面样式不变。

实施与测试证据见 openspec/changes/add-change-delivery-cards/verification.md。合成 UI/API 样本、真实产品只读观察和隔离真实执行分别标注；没有代用户签署业务验收或执行归档。
