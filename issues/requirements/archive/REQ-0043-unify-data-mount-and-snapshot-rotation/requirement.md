# 统一 data 目录边界与本地数据挂载及快照轮转

## 1. 背景

本地默认连接串指向容器内 `/app/data/sqlite/moonbox.db`，数据库设计文档指定宿主机 `data/sqlite/moonbox.db` 为业务库唯一目标路径，但当前 Compose 将 `data/runtime/backend` 挂到 `/app/data`，导致旧路径 `data/runtime/backend/sqlite/moonbox.db` 仍可能作为实际业务库。两处文件均已存在，不能仅按文件名判断内容相同。Chat 执行器的多个 SQLite 属于工作区运行状态，备份目录中的 SQLite 属于平台业务库快照与独立删除日志，应按用途隔离。

Chat 控制器目前在启动时创建一次业务库快照，持续运行约每 24 小时再创建一次，没有自动轮转。旧快照只可通过登记账本的受控过期入口清理。用户已确定继续按用途分目录，要求自动快照默认最多保留 2 份，也允许关闭自动快照。

## 2. 目标用户与目标

- 本地开发及运维人员：能够准确定位当前业务库、执行状态和备份，安全迁移旧数据，并预测磁盘占用。
- Chat 平台使用者：数据库路径调整和备份轮转不影响会话执行、删除记录与可用恢复点。

目标是让本地业务库只有一个明确的持久化入口，并使自动快照的数量可配置、可审计、可安全轮转。

## 3. 范围与边界

### 纳入

- 本地 SQLite 路径、Compose 挂载、部署脚本与环境示例的一致性；检查根 Compose、本地 Compose 及 Chat/Governance overlay。
- 历史业务库位置和快照库存的只读盘点、受控迁移、验证与回滚方案。
- Chat 本地自动快照数量配置、创建与轮转、关闭自动快照、异常报告与恢复保护。
- `data/sqlite/`、`data/runtime/`、`data/tmp/`、对象存储目录的用途、权限、提交边界及相关文档和测试。

### 不纳入

- 将 Codex 执行器运行 SQLite 或删除日志按扩展名搬进 `data/sqlite/`，或把它们合并到业务库。
- 按空间建立独立业务库、改造业务表结构、调整生产 MySQL 存储或提供异机灾备。
- 新增备份管理 UI、用户自行下载备份或自动恢复到在线业务库。

## 4. 功能要求

### FR-001 本地业务库唯一入口

本地 SQLite 模式以宿主机 `data/sqlite/moonbox.db` 对应容器 `/app/data/sqlite/moonbox.db` 为唯一 canonical 业务库。所有启动组合、辅助脚本和文档应指向同一实际文件；启动检查应识别会导致新旧路径分叉的挂载配置，不得静默创建另一份业务库。生产模式继续要求 MySQL，不因本地路径调整回退到 SQLite。

### FR-002 用途目录与访问边界

`data/sqlite/` 承载本地业务库；`data/runtime/` 承载 Chat 执行器状态、治理控制状态及独立备份；`data/tmp/` 承载临时文件。执行器工作区运行文件保持成组存放，备份目录与业务库及恢复目标隔离。私有状态与删除日志维持现有权限限制，运行时数据库、备份、密钥和真实数据继续被 Git 忽略。

### FR-003 自动快照数量配置

增加 `MOONBOX_CHAT_LOCAL_SNAPSHOT_LIMIT`：未设置时取 `2`；配置为正整数时作为自动快照的数量上限；配置为 `0` 时停止启动及周期性自动快照。只接受非负十进制整数，空字符串、负数、小数和其他字符串应显式报配置错误，不能静默回退。该配置不关闭独立删除日志，也不改变手动备份和治理成套备份的显式入口。API 与 Worker 应读取一致的配置并能识别版本不一致。

### FR-004 创建与轮转

配置值大于 `0` 时，延续启动与约 24 小时周期创建节奏。新快照通过 SQLite 完整性、摘要和账本登记校验后，才按创建顺序轮转。数量上限适用于未受保护的自动快照；被治理成套备份引用的快照为受保护例外，不得为了满足数字上限而破坏成套恢复。手动创建的副本保留其显式管理语义，不计入自动快照上限；实现须能区分副本来源，或提供等价的可靠判定。过期操作只能通过受控备份接口更新文件与账本，不能直接按文件名或修改时间删除。

配置值为 `0` 时不产生新自动快照，不因切换配置立即删除历史副本；独立删除日志和已有备份的登记、恢复校验仍可用。备份创建、轮转或过期失败时，保留现有可用恢复点和账本一致性，并输出脱敏错误摘要；不得以未验证新副本替换最后一个有效副本。

### FR-005 删除与恢复保护

会话删除意图在独立日志中持久保存，不能随快照轮转或配置为 `0` 而清空。对历史快照执行恢复时继续重放删除意图，避免已删除内容复活。若某治理成套备份的 manifest 仍引用快照，该快照不得自动过期；成套备份本身的生命周期由显式运维流程管理。

### FR-006 旧数据迁移与清理

迁移前输出源库、目标库及登记快照的清单和磁盘占用，停服并分别备份两个业务库，运行 `PRAGMA integrity_check`、schema 版本与关键表行数对比。两库有差异时暂停自动选择，形成差异报告与明确恢复方案，不覆盖任一现有文件。切换挂载后验证 API、Chat Worker、关键业务数据与重启行为，再按可回滚清单处理 legacy 目录。历史快照先校验账本、摘要、治理引用及删除状态；初次启用上限不应无清单地一次性批量删除，需保留迁移前恢复点并记录每次过期结果。

### FR-007 可观测性与文档

启动校验、快照创建、轮转、跳过受保护副本、过期失败及迁移结果应提供可关联的脱敏运维摘要，不记录连接串凭据、业务正文或本机绝对路径。后续 Change 应按 `docs/standards/product-data-collection-observability.md` 声明 `db`、`task_traces`、`task_trace_spans` 的适用范围和验证；若没有新增 API、Web 行为或请求封装，应写明其 N/A 原因。同步 `.env.example`、本地部署示例、数据目录说明、数据库设计、部署与回滚文档；必要时同步 Git ignore 规则。

## 5. UI 约束

本需求不新增产品 UI。配置错误、磁盘不足或备份失败通过现有部署诊断与运维日志呈现，信息须可定位且脱敏；若后续增加页面入口，须另行明确权限和视觉验收。

## 6. 验收口径

1. 各本地启动组合和辅助脚本解析为同一宿主机业务库；旧路径不再新建业务库，生产 MySQL 路径不受影响。
2. 使用两份内容不同的旧/新库演练迁移：自动流程停止并提供差异，人工确认后可验证切换及回滚；不得发生静默覆盖。
3. 默认值、正整数、`0` 与非法配置均有自动化覆盖；启动重启和周期创建后，未受保护的自动快照数量不超过配置上限。
4. 被成套备份引用的副本、手动副本及独立删除日志不因自动轮转受损；恢复演练不会复活已删除会话。
5. 对现有快照库存有迁移前后数量、摘要、占用和过期结果报告；失败注入时账本仍一致且至少保留此前有效恢复点。
6. 目录权限、Git ignore、环境示例及数据/部署文档与实际挂载一致；Chat 启动、执行、删除和离线恢复回归通过。
