# 用户故事

## US-001 查看 Sprint 总览指标

作为产品负责人，我希望在需求中心顶部指标区看到 Sprint 已完成数量和累计数量，以便快速判断项目迭代闭环情况。

验收要点：
- 指标区展示已完成 Sprint 数与累计 Sprint 数。
- 指标文案能区分“已完成”和“累计”，不让用户误认为是当前筛选结果。
- 无 Sprint 时展示稳定的 `0 / 0` 空态。

## US-002 理解统计口径

作为项目负责人，我希望 Sprint 数量来自 Sprint 生命周期事实源，以便指标能反映真实迭代状态，而不是前端临时卡片或筛选结果。

验收要点：
- 已完成 Sprint 默认按 `iterations/archive/` 统计。
- 累计 Sprint 覆盖 `iterations/change/` 与 `iterations/archive/` 下的有效 Sprint。
- 历史兼容状态不会造成重复计数。

## US-003 筛选看板时保持项目级总览

作为协作者，我希望在搜索、筛选或选择某个 Sprint 后，Sprint 数量指标仍保持项目级总览，以便我在局部查看卡片时仍能理解整体迭代规模。

验收要点：
- 搜索关键字不改变 Sprint 数量指标。
- 对象类型、负责人、优先级和 Sprint 筛选不改变 Sprint 数量指标。
- 卡片列表和已有局部统计仍按筛选条件变化。

## US-004 异常时稳定展示

作为需求中心用户，我希望 Sprint 指标加载失败或解析异常时页面仍可用，以便我能继续查看其他需求与缺陷卡片。

验收要点：
- 加载中不产生布局跳动。
- 接口失败或解析失败时展示可恢复错误态。
- 错误信息不暴露内部路径、堆栈、密钥、token 或治理文档全文。

## US-005 后续实现可被验证

作为开发与测试协作者，我希望该指标有明确 API、前端、观测和视觉验收边界，以便后续 OpenSpec 与实现阶段可以一次性覆盖口径、展示和安全风险。

验收要点：
- 实现阶段有聚合口径测试和前端筛选回归测试。
- API 字段、客户端类型和文档同步范围明确。
- request_logs 与 usage_events 只记录脱敏统计上下文。
