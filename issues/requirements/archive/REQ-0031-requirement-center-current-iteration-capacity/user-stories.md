# 用户故事

## US-001 查看单个当前迭代容量

作为产品负责人，我希望在需求中心进入当前迭代视图时看到当前 Sprint 的已使用容量和总容量，以便判断迭代是否仍有规划余量。

验收要点：
- 页面展示当前 Sprint ID、已使用容量、总容量和容量状态。
- 容量单位沿用 Sprint 容量治理口径。
- 容量展示与当前项目和当前筛选上下文一致。

## US-002 查看两个当前迭代的容量

作为研发负责人，我希望当项目存在 2 个当前迭代时，两个迭代的容量都能被识别，以便避免只关注其中一个迭代造成范围判断偏差。

验收要点：
- 两个当前迭代均显示独立容量项。
- 不静默合并、覆盖或隐藏任一当前迭代。
- 如有汇总信息，必须同时保留分项明细。

## US-003 识别容量风险

作为项目协同成员，我希望容量接近上限、超量或待核实时有清晰但不打断工作的反馈，以便及时发现规划风险。

验收要点：
- 正常、接近上限、已超量和待核实状态有可区分表现。
- 超量状态不自动阻止浏览、筛选或打开文档。
- 容量事实源异常时保留 Sprint ID，并展示待核实状态。

## US-004 理解默认容量与显式容量

作为产品负责人，我希望能区分总容量来自显式配置还是默认规则，以便在需要时追溯容量设置依据。

验收要点：
- 显式容量优先展示。
- 默认容量展示轻量来源提示。
- 缺少事实源时不得伪造默认值。

## US-005 在刷新和项目切换后保持一致

作为日常使用者，我希望手动刷新、项目切换或 Sprint Scope 更新后，容量展示与最新事实源一致，以便看板不会保留过期容量判断。

验收要点：
- 手动刷新后容量随稳定快照更新。
- 切换项目后容量只展示当前项目可访问 Sprint。
- 刷新失败保留上次成功数据并给出轻量失败提示。

## US-006 安全展示容量聚合结果

作为安全审计者，我希望容量聚合只返回安全摘要字段，不泄露不可访问 Sprint、文件路径或敏感配置。

验收要点：
- 无权访问的项目或 Sprint 不通过容量数值、异常提示或搜索结果泄露。
- 请求日志和行为事件只记录脱敏摘要。
- API 响应不包含本机绝对路径、Authorization、Cookie、`.env` 内容或 Markdown 全文。
