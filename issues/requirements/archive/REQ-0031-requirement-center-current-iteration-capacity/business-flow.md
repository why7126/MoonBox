# 业务流程

## 1. 当前迭代容量加载流程

```text
用户进入需求中心
  -> 前端请求需求中心稳定快照
  -> 后端解析当前项目与用户授权
  -> 后端识别当前迭代 Sprint 列表
  -> 后端读取 Sprint scope 与容量事实源
  -> 后端计算每个当前迭代的 used_capacity / total_capacity
  -> 前端在当前迭代指标区域展示容量项
```

关键约束：
- 当前迭代容量必须来自治理事实源或后端聚合结果，不由前端临时推断。
- 同时存在 2 个当前迭代时，输出和展示都应保留分项。
- 请求失败不能清空既有看板，应进入可恢复失败态。

## 2. 容量计算流程

```text
Sprint scope
  -> 收集已纳入的 REQ / BUG / Change
  -> 读取每项容量估算或派生容量
  -> 求和得到 used_capacity
  -> 读取 Sprint 显式 total_capacity
  -> 缺显式配置时读取默认容量规则
  -> 派生 capacity_status
```

容量状态建议：
- `normal`：已使用容量低于风险阈值。
- `near_limit`：已使用容量接近总容量，需关注取舍。
- `over_limit`：已使用容量超过总容量。
- `unknown`：容量字段缺失、冲突或无法计算。

阈值具体数值可在 OpenSpec 设计阶段确认，但必须与 Sprint 容量治理规则一致。

## 3. 多当前迭代展示流程

```text
current_sprints.length = 1
  -> 展示单个容量项

current_sprints.length = 2
  -> 展示两个独立容量项
  -> 如展示汇总，同时保留分项

current_sprints.length > 2
  -> 展示容量待核实或折叠列表
  -> 保留异常说明，不任意选择前两个
```

首版用户明确提出 2 个当前迭代场景，因此 2 个并存是必须支持路径。超过 2 个当前迭代属于事实源异常或治理状态待核实，不在本轮作为正常态扩展。

## 4. 刷新与失败恢复流程

```text
用户点击刷新 / 切换项目 / 外部 Scope 变化后重新进入页面
  -> 重新请求稳定快照
  -> 成功：替换容量项、统计和看板数据
  -> 失败：保留上次成功容量项
  -> 展示轻量失败提示
```

错误提示应说明容量或看板数据刷新失败，但不得暴露文件路径、堆栈或原始文档内容。

## 5. 权限与观测流程

```text
容量查询请求
  -> 请求日志记录 request_id、路径、结果和脱敏摘要
  -> 行为事件记录刷新、筛选或项目切换行为
  -> 权限过滤当前用户不可访问的 Sprint 和项目
  -> 返回安全字段白名单
```

行为事件和请求日志用于排障和产品分析，不参与授权判断。无权对象不得通过容量聚合结果泄露。

## 6. 与父需求差异

REQ-0012 负责需求中心页面骨架、阶段看板、卡片、工具栏和整体视觉。REQ-0031 不重做看板结构，也不新增 Sprint 编辑能力；它只在现有需求中心中补充当前迭代容量可视化、容量状态和异常降级。

与 REQ-0030 的差异：REQ-0030 关注 Sprint 已完成与累计数量指标；REQ-0031 关注当前迭代容量已使用与总容量，不以数量统计替代容量。
