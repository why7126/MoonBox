# 后台用户首次登录激活与冻结前状态恢复

## 背景

MoonBox 已具备管理后台用户管理和后台登录认证基础。当前后台管理员创建用户后，用户状态为“待激活”，但后台登录认证仅允许“正常”状态登录；实际测试路径需要管理员先执行“解冻”把新建用户改为“正常”，再允许其使用临时密码登录。

该语义容易造成两个问题：一是“解冻”被复用为“激活”，不符合管理员和用户对账号生命周期的直觉；二是待激活用户被冻结再解冻后会被直接置为正常，可能绕过首次登录激活流程。账号状态需要区分“用户是否完成首次登录激活”和“账号是否被管理员临时冻结管控”。

本需求采用保守方案：保留现有主状态字段展示和筛选能力，通过新增冻结前状态记录字段或等价持久化能力，在解冻时恢复冻结前生命周期状态，暂不拆分为双状态模型。

## 目标用户

- 后台管理员：需要创建后台用户，并通过清晰的冻结、解冻和状态展示理解账号是否已完成首次激活。
- 新建后台管理员：需要使用一次性临时密码完成首次登录，并在首次登录成功后进入正常账号生命周期。
- 安全审计相关角色：需要追溯账号从创建、待激活、冻结、解冻到正常的状态变化。
- 运维和测试人员：需要验证后台认证与用户管理状态规则一致，避免通过管理操作绕过首次激活。

## 范围

### 包含

- 新建用户默认保持“待激活”状态。
- 待激活的后台管理员允许使用有效临时密码发起首次登录激活。
- 首次登录激活成功后，账号状态自动调整为“正常”，并建立后台登录会话。
- 冻结用户时记录冻结前状态，冻结前状态至少支持“待激活”和“正常”。
- 解冻用户时恢复冻结前状态，不再固定恢复为“正常”。
- 待激活用户被冻结后，解冻应恢复为“待激活”。
- 正常用户被冻结后，解冻应恢复为“正常”。
- 已冻结用户不得登录后台或访问后台 API。
- 前端用户管理操作文案需要避免把待激活用户的解冻暗示为激活完成。
- 后台认证、用户管理 API、数据库约束、审计记录和测试需要同步体现该状态规则。

### 不包含

- 不支持普通前台用户登录管理后台。
- 不新增用户自主注册、邀请邮件、邮箱验证、短信验证、企业 SSO、OAuth 或 MFA。
- 不实现“激活链接”“设置新密码向导”或完整首次登录改密流程。
- 不拆分为 `activation_status` 与 `access_status` 双状态模型。
- 不支持已删除用户恢复。
- 不新增独立审计日志查询页面。
- 不改变系统内置超级管理员保护规则。

## 功能要求

### FR-001 新建用户待激活

后台管理员创建用户成功后，系统 MUST 将新用户主状态设置为“待激活”。

创建结果 MAY 继续返回一次性临时密码，但前端和后端文案 MUST 明确该临时密码用于首次登录激活，不表示账号已处于正常状态。

### FR-002 待激活后台管理员首次登录激活

当待激活用户角色为“后台管理员”且使用有效临时密码登录后台时，系统 MUST 允许其完成首次登录激活流程。

首次登录激活成功后，系统 MUST 将该用户主状态从“待激活”更新为“正常”，并创建后台登录会话。

前台用户即使处于“待激活”或“正常”状态，也 MUST 不得登录管理后台。

### FR-003 正常用户登录

当用户状态为“正常”、角色为“后台管理员”且凭证有效时，系统 MUST 允许其正常登录管理后台。

登录成功后，系统 SHOULD 更新最近登录时间，并返回后台认证所需的 access token、过期时间和当前用户摘要。

### FR-004 冻结前状态记录

后台管理员冻结用户时，系统 MUST 记录冻结前状态，冻结前状态至少支持“待激活”和“正常”。

系统 SHOULD 使用新增 `status_before_freeze` 或等价字段持久化该信息。冻结已冻结用户不得覆盖原冻结前状态。

### FR-005 解冻恢复冻结前状态

后台管理员解冻已冻结用户时，系统 MUST 根据冻结前状态恢复目标用户状态。

如果冻结前状态为“待激活”，解冻后 MUST 恢复为“待激活”；如果冻结前状态为“正常”，解冻后 MUST 恢复为“正常”。

解冻成功后，系统 SHOULD 清空或重置冻结前状态记录，避免后续状态操作读取过期数据。

### FR-006 冻结与登录访问限制

被冻结用户 MUST 不得登录后台，也不得通过已有后台会话继续访问 `/api/v1/admin/**` 管理接口。

冻结成功后，目标用户的有效会话 MUST 按现有用户管理规则失效。待激活用户被冻结时，即使临时密码正确，也 MUST 被拒绝首次登录激活。

### FR-007 删除状态边界

已删除用户 MUST 不得登录、首次激活、冻结、解冻或恢复为待激活/正常状态。

删除用户时，系统 MUST 保留审计追溯数据，不得因为冻结前状态记录导致已删除用户被误恢复。

### FR-008 审计与状态追溯

创建、首次登录激活、冻结、解冻和删除相关状态变化 MUST 记录可追溯信息。

冻结审计 SHOULD 包含冻结前状态；解冻审计 SHOULD 包含恢复后的目标状态。审计记录不得保存明文临时密码、access token 或其他可复用敏感凭证。

### FR-009 兼容现有列表筛选

管理后台用户列表 MUST 继续支持按“待激活”“正常”“已冻结”筛选，并保持默认列表不展示“已删除”用户。

冻结前状态不作为 MVP 的独立筛选项展示。若需要在详情、悬浮提示或确认弹窗中展示“解冻后将恢复为待激活/正常”，应以不破坏现有列表密度为前提。

### FR-010 测试与回归覆盖

系统 MUST 覆盖以下关键回归场景：

- 新建后台管理员为“待激活”，无需管理员解冻即可通过有效临时密码完成首次登录激活。
- 待激活后台管理员首次登录成功后状态变为“正常”。
- 待激活用户被冻结后不可登录，解冻后仍为“待激活”。
- 正常用户被冻结后不可登录，解冻后恢复为“正常”。
- 前台用户不得通过待激活首次登录流程进入管理后台。
- 已删除用户不得通过解冻或首次登录恢复。

## UI 约束

- 用户列表中的“待激活”“正常”“已冻结”“已删除”状态标签应继续保持清晰可辨。
- 对待激活用户，操作入口 MAY 继续提供“冻结”；不得提供会让管理员误以为已经完成用户本人激活的“解冻即激活”文案。
- 对已冻结用户，解冻确认弹窗 SHOULD 提示解冻后将恢复到冻结前状态，例如“解冻后恢复为待激活”或“解冻后恢复为正常”。
- 新建用户成功后的临时密码弹窗 SHOULD 明确该密码用于首次登录激活，关闭后不再展示。
- 登录失败文案不得泄露账号是否存在、冻结前状态字段、密码哈希或内部状态细节。
- 深浅主题下，状态标签、解冻提示、错误反馈和敏感结果弹窗必须保持可读。
