# 用户故事

## US-001 新建后台用户保持待激活

作为后台管理员，我希望新建用户后账号保持“待激活”，以便区分“账号已创建”和“用户本人已完成首次登录”。

验收要点：

- 创建后台用户成功后，用户主状态为“待激活”。
- 创建结果返回的一次性临时密码仅用于首次登录激活，不表示账号已经正常启用。
- 用户列表、筛选和状态标签能展示并筛选“待激活”用户。
- 默认列表仍不展示“已删除”用户。

## US-002 待激活后台管理员首次登录自动激活

作为新建后台管理员，我希望使用临时密码首次登录后账号自动激活，以便无需管理员额外执行“解冻”才能进入后台。

验收要点：

- 待激活且角色为“后台管理员”的用户使用有效临时密码登录时，系统允许完成首次登录激活。
- 首次登录激活成功后，用户状态变为“正常”。
- 首次登录激活成功后，系统创建后台会话并返回正常登录结果。
- 前台用户不得通过该流程进入管理后台。

## US-003 冻结待激活用户不破坏激活流程

作为后台管理员，我希望可以冻结待激活用户，并在解冻后恢复为待激活，以便临时管控账号时不绕过用户本人首次登录激活。

验收要点：

- 待激活用户允许被冻结。
- 冻结待激活用户时，系统记录冻结前状态为“待激活”。
- 冻结期间，用户无法登录后台或完成首次登录激活。
- 解冻后，用户恢复为“待激活”，仍需通过首次登录成功后才转为“正常”。

## US-004 解冻正常用户恢复正常

作为后台管理员，我希望正常用户被冻结后解冻能恢复为正常状态，以便账号临时管控结束后恢复原有访问能力。

验收要点：

- 正常用户被冻结时，系统记录冻结前状态为“正常”。
- 冻结成功后，目标用户已有后台会话按规则失效。
- 解冻后，用户恢复为“正常”。
- 解冻操作不得把已删除用户恢复为可用状态。

## US-005 追溯状态变化与敏感结果

作为安全审计相关角色，我希望账号创建、首次登录激活、冻结和解冻状态变化都有审计依据，以便追溯账号生命周期。

验收要点：

- 首次登录激活、冻结、解冻和删除产生可追溯状态变化记录。
- 冻结审计能体现冻结前状态，解冻审计能体现恢复后的状态。
- 审计和日志不得记录明文临时密码、access token 或其他可复用敏感凭证。
- 登录失败文案不得泄露账号是否存在、冻结前状态字段或内部鉴权细节。

## US-006 理解解冻后的恢复状态

作为后台管理员，我希望在解冻确认时看到解冻后的恢复状态，以便知道目标账号会恢复为“待激活”还是“正常”。

验收要点：

- 已冻结用户的解冻确认弹窗提示解冻后的目标状态。
- 待激活用户冻结后，解冻提示应表达“恢复为待激活”。
- 正常用户冻结后，解冻提示应表达“恢复为正常”。
- 状态变更确认使用设计系统确认弹窗，不调用 `window.confirm`。
