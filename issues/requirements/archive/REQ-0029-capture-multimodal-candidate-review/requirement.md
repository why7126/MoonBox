# 新建 Capture 图文整理与候选审阅

## 1. 背景与来源

本需求承接 `capture.md` 和本次 `/req-explore` 对话。用户已确定流程为“原始图文 → AI 分类拆分与完善 → 用户审阅调整 → 确认 → 分配编号并落盘”，以项目在 Codex 中执行 `/capture` 的分类、拆分、内容整理效果为基线。

现有新建 Capture 要求用户填写类型、标题与分级，描述上限 200 字，服务端单次创建一条采集记录。已有服务端编号、幂等请求、项目写入协调与失败恢复基础；现有治理候选用于已有 REQ 的 PRD 生成，不能直接代表本需求的未编号候选。当前 Codex 执行适配以文本作为轮次输入，图片传递及模型可读性需要落实到完整链路。

上述为探索时的代码观察，不代表线上验证结果。参考入口：`src/backend/app/schemas/requirement_center.py`、`src/backend/app/governance/capture.py`、`src/backend/app/governance/writer.py`、`src/backend/app/governance/candidates.py`、`src/backend/app/chat/app_server.py`、`src/web/src/pages/catalog/RequirementCenterPage.tsx`。

## 2. 目标用户与价值

面向在需求中心收集需求、反馈与问题的产品负责人、研发成员及项目协作者。用户直接提交文字和图片，由 AI 形成可审阅候选，在正式创建前纠正类型与内容，减少结构化录入、误分类改号和重试重复创建。

交付结果以一批混合图文完成真实整理、用户调整、确认创建和来源回查为准；AI 运行结束、候选保存成功、创建任务受理均不等同于正式 Issue 创建成功。

## 3. 范围

### 3.1 包含

- Web 需求中心“新建 Capture”的原始文字与图片输入。
- 复用 `/capture` 分类、拆分和整理规则形成多条无正式编号的候选。
- 候选改类型、编辑标题/分级/描述、合并、拆分、删除与图片关联维护。
- 原始材料及候选草稿保存、最终版本确认、服务端按最终类型分配编号。
- 混合 REQ/BUG 批量采集记录创建、注册表和索引同步、来源追溯及幂等恢复。
- 项目授权、附件访问控制、状态真实性和数据采集链路观测。

### 3.2 不包含

- 自动生成正式 `requirement.md`、`bug.md`、六件套、OpenSpec Change，或自动评审、纳入 Sprint、开发与归档。
- 修改 Codex 中直接执行 `/capture` 的既有用户工作流；本需求在产品内建立审阅边界。
- Chat 工作台的整体视觉改造、Skill 快速引用及任意文件类型上传。
- 在候选阶段创建正式 Issue、预占正式编号，或先分配 BUG 再因用户改类型而换成 REQ。
- 首版多人同时协作编辑同一候选草稿的完整协作产品；服务端仍需防止多窗口或并发请求覆盖。

## 4. 产品流程与身份

```text
原始文字与图片
  → AI 整理
  → 候选审阅与修改
  → 确认最终候选版本
  → 服务端编号和批量落盘
  → 创建结果及来源回查
```

| 对象 | 职责 | 正式编号 |
|---|---|---|
| 原始材料与草稿批次 | 保存用户输入、图片引用、项目归属与草稿状态 | 无 |
| 候选条目 | 使用稳定内部标识保存内容、建议类型、来源关系及修改版本 | 无 |
| 确认任务 | 绑定不可变的最终候选版本，记录创建进度与恢复结果 | 仅确认后由服务端分配 |
| 正式 Issue | 按最终类型进入 `issues/requirements/plan/` 或 `issues/bugs/plan/` | REQ 或 BUG |

“条目 1、条目 2”仅是当前展示顺序，不作为图片关联、幂等或来源追溯标识。草稿状态与正式 Issue 的 captured/draft 生命周期分别管理，不把未确认候选计入正式采集池。

## 5. 功能要求

### FR-001 原始图文输入

用户可直接输入需求或问题描述并附图片，无需预填类型、标题与分级。支持多图片选择、预览、移除和上传结果反馈；数量、格式、体积和文本长度采用服务端能力返回、前后端一致的明确限制，首版阈值见第 10 节。不能沿用现有 200 字描述限制而截断原始反馈。文字与图片均为空时不发起整理。

图片未上传成功或模型无法读取时明确提示，不伪装成已理解图片；重试保留已成功材料及用户输入。首版支持仅图片输入；仅当内容不足以判定时产生待澄清项，不要求用户重复描述清晰可读的图片。

### FR-002 AI 分类、拆分与完善

以仓库 `/capture` 的规则为基线：已有能力或规范下的偏差倾向 BUG，尚未交付的新能力或流程倾向 REQ；混合输入按独立交付与验收边界拆分，同一交付单元的细节保持单条。分类参考所选项目的授权上下文，证据不足标记待澄清，不虚构已有规格、根因或复现事实。

每条候选包含内部标识、建议类型、标题、对应分级、整理描述、来源依据和待澄清项。候选描述保留背景、诉求或实际/期望差异，为后续生成阶段提供材料，内容完善不扩展为正式 PRD 或缺陷分析报告。保留 AI 初判与用户最终决定的区别。

### FR-003 整理与写入隔离

候选整理阶段不具备向正式 Issue 目录、注册表或索引写入以及消耗编号的能力。现有 `/capture` 技能包含落盘步骤，产品内复用需限定为整理规则和结果契约；不能仅依赖提示模型“暂不落盘”作为写入边界。AI 输出经过服务端结构与范围校验才进入审阅，非法结果不会触发创建。

### FR-004 候选审阅编辑

按“条目 1、条目 2”展示候选，支持修改类型、标题、分级、描述、合并、拆分和删除；保留来源预览入口。编辑与改类型沿用稳定内部标识，不丢失正文和图片。REQ 使用 priority，BUG 使用 severity；改类型后使用目标类型的分级建议并供用户审阅，不直接映射两类分级，不将异类字段写入正式文档。

合并与拆分明确产生的新条目及其来源关系，不能用列表下标重新绑定图片。删除条目不删除其他候选引用的材料。所有候选被删除后禁止确认空批次。若提供重新 AI 整理，不静默覆盖已保存的人工修改。

### FR-005 草稿保存与恢复

确认前只保存原始材料与候选草稿，保存结果区分保存中、已保存、失败；保存失败不显示已保存，也不使用未知版本确认。草稿与附件受所选项目及用户权限约束，切换项目后不展示旧项目的迟到结果。

采用服务端自动保存：停止输入 1 秒后保存，变更持续发生时最长 5 秒触发一次；确认前等待最新版本保存成功。关闭或刷新后可从新建 Capture 的“恢复草稿”入口恢复。关闭和取消只退出当前界面，不删除草稿或创建 Issue；保存失败时提供重试与保留本次内容的退出提示。草稿保留及删除规则见第 10 节。

### FR-006 最终版本确认

确认前汇总最终 REQ/BUG 数量及全部将创建的候选；本期确认当前保留的完整候选集合，排除条目通过删除或合并完成。服务端核对候选版本、项目绑定、权限、材料有效性与字段合法性；过期版本返回冲突并保留用户修改，不静默采用其他版本。

成功受理后固定确认版本，创建任务不再随草稿编辑变化。重复点击返回既有任务结果；确认后需要修订时按任务状态明确处理，不能改变正在落盘的内容。前端按钮禁用仅用于体验，不能替代服务端并发校验。

### FR-007 按最终类型分配编号

服务端在确认之后使用当前项目的对应注册表和目录占用情况分配编号，并协调同项目并发写入。客户端和模型不指定正式编号。编号分配结果绑定确认任务，恢复时复用已确定结果，不重新分配同一候选编号。

例如“条目 2”由 BUG 改为需求后，只分配 REQ 编号并写入需求目录；反向修改同理。保留候选内部标识到最终 Issue 完整身份的映射。

### FR-008 批量生成采集记录

对最终 REQ 与 BUG 分别生成 `plan/` 下的对应目录、`capture.md`、`trace.md`，维护类型对应注册表及当前态索引。正式状态为 captured，iteration 为空，关联 Change 为空；分级以最终确认值写入 trace 和 capture，并同步注册表。

保留来源命令语义 `captured_via: capture`、分类依据及用户调整依据；AI 初判与最终类型不混淆。正式目录不生成 `requirement.md` 或 `bug.md`，后续由对应 generate 命令处理。创建成功需核对目标记录、编号映射、注册表和索引一致，并刷新真实看板。

### FR-009 幂等与失败恢复

对重复点击、请求超时、响应丢失、并发提交和中途失败重试，同一批次同一确认版本不重复创建。幂等键与请求内容一致性校验之外，还需防止更换请求键重复创建同一已确认版本；幂等的业务作用域包含授权项目及确认身份，不能跨项目复用结果。

已分配编号和已写文件保留可恢复依据；重试读取原任务，续作未完成步骤或返回已完成结果。外部修改造成冲突时不覆盖外部内容，提供明确状态和恢复入口。失败结果保留输入与确认依据，不要求用户重建整批材料。

采用整批一个创建任务：确认后固定版本，失败时续作该任务，所有目标记录、注册表及索引校验完成后才报告成功；未终态期间看板保持上一个完整快照并显示创建中或恢复提示。文件系统多文件写入不等于原子事务，不能在 PRD 或界面承诺未经实现验证的瞬时全有或全无；不完整状态不能被报为整批成功。

### FR-010 来源追溯与图片引用

从最终 Issue 可回查原始文字、关联图片、AI 分类依据、人工调整及最终确认版本；从创建结果可反查候选与正式编号。合并和拆分保留多来源关系，图像引用使用稳定受控标识，不使用展示序号、临时地址或本机路径作为长期来源。

业务原始材料与观测摘要分别保存。来源访问重新校验授权；附件保留与删除策略需兼顾正式记录的追溯需求，不因草稿清理静默造成正式记录图片失效。关联存储方式与脱敏投影在后续设计中落实。

### FR-011 任务状态与权限

界面区分整理中、待审阅、保存失败、确认中、创建中、创建成功、可重试失败、冲突和需恢复状态。AI 失败不会分配编号；请求受理不会提前显示创建成功。刷新后的结果来自服务端事实，不通过聊天文本或本地临时列表推断。

读取、整理、草稿修改、确认、附件访问及结果查询均校验用户与项目范围；无权限或项目不可写时解释原因并保留可安全展示的输入，不回退到其他仓库、示例数据或绕过治理边界。

## 6. UI 约束

沿用需求中心现有设计 token 与组件体系。主要交互分为图文输入、候选审阅、创建结果三个状态；候选较多时保留可滚动列表及清晰的确认汇总，不把所有内容塞进原有短表单。用户已确认正式方向为“单一 MD 编辑器 + 内嵌图片/文本文件材料块”：Capture 弹窗只有一个可编辑文本/MD 编辑框，用户在其中输入原始描述；`.txt`/`.md` 文件内容导入为编辑器内来源块，图片作为同一材料流的材料卡展示、上传和移除。桌面宽度不超过 1200px，右侧可展示只读材料摘要或候选审阅；窄屏转单列。

审阅阶段不展示 REQ/BUG 正式编号；界面称“类型”“需求优先级”“缺陷严重度”，内部标识和版本号不作为必填字段。按钮、编辑区、图片预览、合并/拆分动作具备清晰标签、键盘访问和焦点恢复。关闭、返回、刷新与项目切换都需覆盖未保存内容和进行中任务。

本次已在 `prototype/web/` 补齐交互原型、原型拆解和动作矩阵；原型使用演示数据，实施按项目要求建立 UI Contract、UI Skeleton、动作与 modal 映射，完成 1440px、关键交互及 computed style 证据；没有用户提供的视觉附件，不虚构附件复刻验收依据。

## 7. 一致性、安全与观测

API 需覆盖草稿、候选版本、整理任务、确认和结果查询，具体路径与 schema 留到 Change 设计；同步 OpenAPI、客户端生成和请求封装。持久化涉及草稿、来源、确认映射及恢复证据，数据结构、SQLite/MySQL 兼容性与对象存储边界需同步数据库和部署文档。优先复用现有可信写入与执行机制，不能将现有单条测试当作批量实现已通过的证据。

依据 `docs/standards/product-data-collection-observability.md`：

```yaml
product_data_collection_observability:
  status: applicable
  affected_layers:
    - usage_events
    - request_logs
    - task_traces
    - task_trace_spans
  reason: 图文上传、AI 整理、候选审阅、确认及批量写入跨越 Web 行为、API 请求与多步骤任务，四层均适用，无层级 N/A。
  validation: 本次完成 PRD 声明核对；实施后验证行为到服务端 request_id、整理与创建任务节点的关联，覆盖失败重试、脱敏、可信字段和观测故障降级；真实行为验证与合成回归分别记录。
```

事件名采用稳定字典；观测 metadata 仅保存允许的标识、数量和结果摘要，不记录完整图文、模型输入输出、凭证和本机路径。服务端生成可信 request_id，直接 API 不伪造界面行为；观测失败不阻断主流程但保留降级摘要。观测明细沿用标准保留策略，业务草稿与图片期限独立决定，不能套用日志期限自动删除来源。

## 9. 验证方向

- 同一组混合文字、截图及模糊反馈分别通过 Codex `/capture` 整理基线和产品候选链路，人工核对分类依据、合理拆分、内容保真与待澄清标识；不要求逐字一致。
- 验证类型双向修改、编辑、合并、拆分和删除后内容与图片关联不丢失，确认前正式目录和编号计数不变。
- 验证过期候选、同时确认、换键重复请求、响应丢失和每个写入阶段故障后的恢复，检查一候选一正式身份及索引一致性。
- 验证纯 REQ、纯 BUG 和混合批次只生成采集产物，后续 generate 路由正确。
- 验证权限失效、项目切换、图片读取失败、模型不可用及观测降级，分别记录真实 UI 观察与合成回归。

详细验收清单见 `acceptance.md`；用例已随 Change 实施、返修和归档完成验证，原型操作验证未被用作产品行为验收替代。

## 10. 已收敛决策与首版约束

用户在本次 `/req-complete` 明确“用户决策点按推荐建议”。D-001、D-002 按此前推荐落实；D-003、D-004 按推荐方向补齐以下首版设计默认值，数值由本次文档完善提出，不冒充用户逐项指定。

| 标识 | 首版约束 | 依据与边界 |
|---|---|---|
| D-001 | 服务端自动保存，输入停止 1 秒触发、持续输入最长 5 秒触发，确认前等待保存；本人在同一授权项目可恢复草稿 | 防止人工调整丢失；保存失败时阻止确认，保留当前内容并提供重试 |
