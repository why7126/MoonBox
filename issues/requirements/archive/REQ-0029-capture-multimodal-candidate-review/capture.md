# 一句话

新建 Capture 支持原始图文输入，沿用项目在 Codex 中执行 `/capture` 的分类、拆分和内容整理效果，增加候选审阅环节，并在用户确认后按最终类型分配正式编号、幂等批量生成采集记录。

# 原始描述

用户确定流程：**原始图文 → AI 分类拆分与完善 → 用户审阅调整 → 确认 → 分配编号并落盘**。

| 阶段 | 已确定行为 |
|---|---|
| 原始输入 | 用户描述问题或需求并附图片，无需填写类型、标题、分级。 |
| AI 整理 | 形成多条候选，建议类型、标题、分级与描述，保留来源依据；沿用 Codex `/capture` 的分类、拆分及内容完善效果。 |
| 用户审阅 | 用“条目 1、条目 2”展示；支持修改类型、编辑内容、合并、拆分、删除；不展示或预占 REQ/BUG 编号。 |
| 确认创建 | 按最终类型分别由服务端分配 REQ/BUG 编号，批量生成对应阶段目录、`capture.md`、`trace.md`，同步注册表与当前态索引。 |

用户示例：AI 将“条目 2”判断为 BUG，用户改为需求后，最终分配 REQ 编号，不先产生 BUG 再改号。

## 已确定边界

- 候选使用内部稳定标识保存编辑内容和图片关联，类型变化不会丢失内容；展示序号与内部标识、正式编号相互区分。
- 确认前只保存原始材料与候选草稿，不写入正式 Issue 目录，不消耗或预占编号。
- 确认绑定最终候选版本，由服务端分配编号；重复点击、并发提交或失败重试不得重复创建。
- 来源追溯覆盖原始文字、图片、AI 分类依据、用户最终审阅版本与创建结果；合并、拆分和类型变更后仍保留来源关联。
- 分级随最终类型采用对应字段：REQ 使用 priority，BUG 使用 severity；两类分级不直接互相映射。
- 确认后的产物遵循 `/capture` 采集边界：先生成采集记录，正式 `requirement.md` / `bug.md` 留到后续生成阶段。“落地深度”已收敛，无需再次选择。

## 目标用户与价值

面向在需求中心提交需求与问题的产品、研发及团队成员，减少结构化录入负担，让用户能在形成正式 Issue 前纠正 AI 判断，避免误编号和重试造成重复条目。

## 拆分与分级初判

本次保持一条需求：图文输入、AI 整理、候选审阅、确认编号和幂等落盘共同构成新建 Capture 的单一交付与验收闭环。暂定 P1，依据为核心采集入口的体验与数据一致性增强，用户未指定更高紧急等级。

REQ-0027-capture 是部署验收测试记录，与本需求不同；本次不覆盖该记录。现有需求中心能力与 Capture 持久化修复作为后续探索的关联背景，不宣称已满足本需求。

## 建议验收要点

1. 输入包含多项需求、缺陷与图片时，AI 输出多条候选及其来源依据；无需用户预先填写结构化字段。
2. 候选编辑、改类型、合并、拆分、删除后，内容和图片关联正确，正式编号仍未分配；取消或仅保存草稿不产生正式 Issue。
3. BUG 候选改为 REQ 后只生成 REQ 记录，反向变更同理；正式分级字段与最终类型一致。
4. 确认所用候选版本与用户审阅版本一致；过期版本或确认期间变更不被静默创建。
5. 混合类型批量确认生成对应的 `plan/` Issue 目录、`capture.md`、`trace.md`，注册表和索引一致，不生成 `requirement.md` / `bug.md`。
6. 重复点击、并发确认、响应丢失和部分落盘后失败重试不重复生成 Issue，能够回查确认批次与最终创建结果。
7. 从最终 Issue 可追溯来源材料、候选及确认版本，合并与拆分的来源关系可核验。

# 决策承接

用户在 `/req-complete` 指定“用户决策点按推荐建议”。已采用自动保存可恢复和整批固定版本续作；材料长期追溯、容量限制、输入阈值及质量样例按推荐方向在 `requirement.md` 第 10 节补齐。具体数值为本次文档完善的首版默认值，不是用户逐项指定值。

原始材料和草稿不进入正式 Issue 目录；确认后只生成采集产物的边界保持不变。
