# 用户故事

## US-001 从当前迭代容量区域发现归档入口

作为产品负责人，我希望在当前迭代已有工作量时，从当前迭代容量区域或操作区发现“归档当前迭代”入口，以便在迭代收尾阶段不用离开需求中心也能进入归档确认流程。

验收要点：
- 当前迭代 `used_capacity > 0` 人天时，用户能在容量区域或操作区发现归档入口。
- 入口明确绑定目标 Sprint，多个当前迭代时不会误导用户归档其他 Sprint。
- `used_capacity = 0`、无当前迭代或容量待核实时，不提供可执行归档入口。

## US-002 归档前确认目标 Sprint 与风险

作为项目负责人，我希望点击归档入口后先看到确认流程和门禁状态，以便在执行前确认目标 Sprint、容量摘要、归档影响和当前阻塞项。

验收要点：
- 点击入口后进入确认流程，不直接执行归档。
- 确认流程展示目标 Sprint ID、当前状态、容量摘要和归档影响。
- 用户取消确认后，不改变 Sprint、REQ、BUG、Change 或 Workflow Sync 状态。

## US-003 不能绕过 Sprint archive 门禁

作为治理维护者，我希望归档入口复用 Sprint archive 既有门禁，以便前端新增入口不会绕过未归档 Change、验收报告 sign-off、权限或 Workflow Sync 校验。

验收要点：
- 未归档 Change、验收报告未 sign-off、权限不足或 Workflow Sync 校验失败时，归档不能执行。
- 门禁失败时展示失败项和修复方向，而不是展示强制归档入口。
- 门禁通过后才允许继续归档执行。

## US-004 权限不足时安全反馈

作为无归档权限的协作者，我希望页面不会让我误以为自己可以归档当前迭代，同时也不会泄露我无权查看的 Sprint 或内部治理细节。

验收要点：
- 无权限用户不能执行归档。
- 如展示禁用态，禁用原因是安全摘要，不泄露不可见 Sprint、内部路径、堆栈、密钥或 `.env` 内容。
- 前端禁用态与后端权限结果保持一致。

## US-005 归档完成或失败后保持看板一致

作为研发与测试协作者，我希望归档成功或失败后需求中心状态仍与事实源一致，以便不会把已归档 Sprint 误当成当前迭代继续推进。

验收要点：
- 归档成功后刷新当前迭代、容量、Scope 和卡片状态。
- 归档失败时保留当前上下文并展示轻量失败信息。
- Workflow Sync 刷新失败时提示状态可能过期，不伪装成归档成功。
