# 移除新建 Capture 草稿的项目绑定版本校验

## 1. 背景与目标

用户在新建 Capture 弹窗遇到“草稿项目绑定已变化”，无法恢复既有内容。用户已明确选择完全删除绑定版本一致性校验，并以本需求关联已归档的 REQ-0029，保留原交付历史。本需求继承 P1 优先级。

目标是同一用户、同一授权项目的旧草稿不再仅因连接配置版本变化而失效，能够继续恢复、保存、处理图片、AI 整理及确认创建。绑定版本不是草稿内容版本，也不是项目身份或写权限；删除前者的相等性门禁，仍保留后三者的实际校验。

## 2. 目标用户

使用 Web 需求中心采集需求、反馈和缺陷的产品负责人、研发成员及项目协作者，尤其是保存草稿后项目连接配置发生变化的用户。成功标准是旧草稿可继续完成原业务流程且不会越权、重复创建或误写其他项目。

## 3. 范围

包含草稿创建、列表与恢复、保存及删除、图片上传与读取、整理任务提交和结果读取、确认创建、确认任务查询和失败续作中实际使用的绑定版本门禁。确认批量落盘过程中使用公共写入器的 Capture 分支同样纳入核对。

不包含跨用户共享、草稿跨项目迁移、重构其他治理动作的绑定规则、修改 AI 分类策略、MD 编辑器能力或界面整体改版。不要求删除数据库中的 binding_revision 字段；历史值可作为追溯信息保留，但不能继续充当 Capture 旧草稿的准入条件。本轮只生成 PRD 及同步治理状态，不实施 API、数据库或业务代码变更。

## 4. 现状核对与策略差异

以下为当前代码及文档静态证据，不代表产品运行态复现或测试通过。

| 入口 | 现有证据 | 本需求要求 |
|---|---|---|
| 草稿读取、保存、删除 | capture_drafts.py 的 get 比较草稿 binding_revision；authorize 比较两次授权快照版本 | 移除版本不相等的独立拒绝，继续按当前身份授权并校验所有者、项目与状态 |
| 上传与图片读取 | capture_media.py 调用 drafts.get / authorize | 旧草稿材料不因版本不同被拒绝，继续校验材料归属和可读性 |
| AI 整理及结果查询 | capture_organizer.py 提交、执行、结果读取和执行后复核调用 drafts.get | 保留当前权限复核和草稿内容版本约束，绑定版本变化不单独导致任务失败 |
| 确认、状态及来源查询 | capture_confirmations.py 使用 service.get / authorize | 旧草稿确认与查询可继续，仍冻结最终版本并检查权限、材料与幂等 |
| 失败续作 | capture_confirmations.py 的 retry 比较操作记录 binding_revision | 删除独立版本门禁，保留原任务、原映射和文件冲突检查 |
| 持久化写入边界 | writer.py 的 refresh_capture_authorization 及操作执行路径比较绑定版本 | 核对 Capture 专属路径及公共路径调用，避免底层遗留门禁；不全局取消其他动作的保护 |

代码路径均位于 `src/backend/app/governance/`。`openspec/specs/capture-candidate-review/spec.md` 的“整批恢复与真实终态”当前将绑定变化列入恢复阻断；未来 Change 需修改对应策略，保留权限撤销、损坏计划和第三种文件内容的拒绝规则。API 索引中的“每次请求复核项目绑定”需明确区分当前项目有效性与历史版本相等性。

## 5. 功能要求

### FR-001 旧草稿持续可用

同一所有者、相同 space_id / repository_id 且具备当前权限时，无论草稿记录的绑定版本是否等于当前版本，用户均可读取和继续操作。不得通过自动清空、丢弃旧草稿、要求新建草稿或批量重写历史版本来规避这一目标。已删除草稿和非法状态仍按既有规则处理。

### FR-002 按当前项目授权

每个请求及异步任务关键写入边界重新获取当前项目权限与服务端解析的目标。空间、仓库、草稿所有者和材料归属保持一致；客户端不能提交文件路径替代服务端目标。撤权、项目失效和只读项目的写请求继续拒绝；有读权限的只读用户是否可查看沿用既有读权限规则。执行过程中发生变化时，不能继续使用失效授权或将旧目标的写入计划无条件套用到新目标。

### FR-003 保存、材料与整理

保留 expected_revision / revision 并发控制、材料状态与配额、候选来源和 AI 迟到结果规则。绑定版本变化后可保存文字和候选、上传及预览归属合法的旧图片、重新整理和获取建议；旧整理结果不能覆盖人工新版本。绑定版本和内容 revision 不能合并处理。

### FR-004 确认创建与幂等

确认前检查最新已保存版本、全部候选、材料及当前写入就绪状态，以当前授权项目冻结业务确认快照。重复确认、换幂等键和网络重试复用原确认任务，不能因绑定变化重新分配编号或重复创建。仅在整批文件、注册表、索引和映射校验完成后展示创建成功。

### FR-005 未完成任务恢复

删除确认重试及实际执行路径中仅凭 binding_revision 不同拒绝恢复的条件。仍复用持久化任务、编号映射、before/after 证据及项目锁；文件出现第三种内容、计划损坏、目标不可验证或权限不足时保留原任务并说明可操作原因，不能伪装成成功或重建一批 Issue。

仅版本变化、实际写入目标与内容基线保持可验证一致时应可续作。实际治理目录被重新指向，尤其已有部分文件落盘时，如何对原目标与当前目标完成一致性判断仍待第 9 节评审；不得默认跨目标自动搬迁、复制已确认结果或删除原文件，也不得把历史版本相等性换名重新引入。

### FR-006 用户反馈与追溯

移除“草稿项目绑定已变化”及同义的纯版本阻断提示。实际权限、材料、内容冲突、未就绪和恢复证据错误仍给出对应中文原因及操作指引，用户输入保留。项目身份以当前已授权的空间和仓库展示；禁止显示内部绝对路径、凭证或原始绑定配置。任务及来源追溯继续关联原草稿、候选、确认版本和最终 Issue。

## 6. UI 约束

沿用现有新建 Capture 弹窗、草稿列表、保存状态及任务结果布局；确认需等待最新保存完成。不新增让用户手动修复 binding_revision 的按钮或表单。本需求无新原型附件，不涉及参考稿复刻；后续若增加写入目标提示，在需求完善阶段确定用户可理解的项目标识及确认时机。

## 7. 一致性、安全及观测

遵循 `docs/standards/product-data-collection-observability.md`。复用可信 request_id、既有 Web 行为关联及整理/确认/恢复 Task Trace；直接 API 和轮询不伪造用户行为，普通草稿读写不因本需求新增任务链路。错误摘要区分权限、内容冲突和恢复证据问题，不记录完整草稿、图片、Prompt、绑定配置或本机路径。

观测声明中的各层为影响核对与回归范围，并非承诺新增表或字段。管理端、移动端和小程序为 N/A：本需求只改变 Web Capture 服务链路；部署拓扑、对象存储布局及保留周期为 N/A：没有新增存储介质、迁移或清理策略。对象存储授权读取、Web 请求封装、现有 usage_events 仍需回归，不能因无新增字段而省略关联验证。

实施时同步 API 错误语义、DB 字段用途说明、UI 用户说明、安全边界记录及相关测试；若响应或请求结构发生变化，再同步 OpenAPI 与客户端生成物。现阶段不预设数据库迁移，不修改正式规格或已归档 REQ-0029。

## 8. 验证方向

| 场景 | 可核对结果 |
|---|---|
| 同用户同项目，保存后真实修改绑定配置版本 | 恢复、保存、删除、图片读取/上传、整理、确认和查询均无纯版本拒绝 |
| 仅版本变化的未完成确认任务 | 同任务及原编号恢复，最终仅一批 Issue，记录可回查 |
| 治理目标重新指向，包含部分写入 | 按待评审恢复契约验证，无跨项目误写、无重复编号、无静默迁移 |
| 跨用户、跨项目、撤权、只读写入 | 请求拒绝且无业务副作用，不能借历史草稿绕过当前权限 |
| 多窗口旧 revision、重复/换键确认、执行中断 | 保留版本冲突、不可变确认快照和原有幂等恢复 |
| 材料不归属当前草稿、失效图片、外部文件冲突或损坏计划 | 返回真实原因，保留输入或原任务，不降低安全门禁 |
| Web 与直接 API、异步任务观测 | 请求与任务关联正确，API 不伪造行为，摘要脱敏 |

实施验证需覆盖 SQLite 与 MySQL 兼容路径中的授权和并发语义，并包含真实配置变化场景；只改测试内版本字符串不能替代最终运行态观察。本轮仅完成文档与静态调用点核对。
