# 九阶段流转规范查阅与研发规范中心

## 1. 背景与目标

用户希望在推进研发工作时随时理解阶段流转要求，并能集中查看当前完整研发规范及其变化历史。已选择“阶段摘要＋完整原文＋迭代日志”：两个入口引用同一规范来源，支持版本追溯，首期只读。

目标是降低规则查找和理解成本，避免阶段说明与完整规范不一致。这里的研发规范包括流程、交付要求、质量门禁及专项规范；具体需求的 OpenSpec 规格属于关联产物，不与团队研发规范混为一类。

现状依据为需求中心源码中的九阶段定义、项目治理规则及采集记录。本次未验证运行态布局，不宣称现有产品缺少或已经提供某个入口。

## 2. 目标用户与场景

- 产品负责人：查阅评审、迭代纳入及验收要求。
- 开发与测试成员：查阅启动条件、交付材料、质量门禁及返修要求。
- 团队新成员：集中阅读规范并通过迭代日志了解变化原因。

核心场景：在阶段列打开流转规范，阅读摘要，按需跳到完整原文；在独立规范中心查找当前规范、来源版本和历史日志。

## 3. 范围与非目标

包含九阶段规范入口、阶段摘要、完整原文阅读、规范分类与搜索、规范迭代日志、来源版本追溯、只读权限及异常状态。

不包含在线编辑规范、规范审批发布、修改现有阶段流转门禁、自动执行技能命令、自动补写缺失规范、跨项目全局搜索、通用 Git 浏览器、自动生成历史差异或修改既有研发规范内容。规范中心不是仓库任意文件浏览器。

## 4. 功能要求

### FR-001 九阶段入口与流转覆盖

每个阶段列标题附近提供“流转规范”入口，即使该列没有卡片也能使用。入口与卡片业务操作独立；打开规范不触发状态流转。

| 当前阶段 | 下一阶段或结果 | 核心内容 |
|---|---|---|
| 采集池 | 规划中 | 信息完整性、重复检查、需求与缺陷分流 |
| 规划中 | 待评审 | 文档补齐、范围与验收标准 |
| 待评审 | 已评审或评审处置 | 通过、退回、延后或不做的条件 |
| 已评审 | 迭代规划 | 纳入迭代、优先级、容量和依赖 |
| 迭代规划 | 待开发 | OpenSpec 生成和文档完整性 |
| 待开发 | 研发中 | 启动条件、授权范围和准备事项 |
| 研发中 | 验收中 | 实现、自检、测试、文档同步与完成门禁 |
| 验收中 | 已完成或返修 | 逐项验收、证据、归档和返修规则 |
| 已完成 | 历史追溯 | 归档资料及后续变更说明，无虚构下一阶段 |

阶段说明遵循实际规则，不把界面列序当作唯一状态机。验收返修说明执行期间展示研发中、完成后回到待复验，保留原 Change 执行事实。

### FR-002 阶段摘要

摘要包含目标阶段、适用对象、进入下一阶段的条件、所需文档和证据、操作或命令、确认角色、失败或退回分支。REQ、BUG 的不同要求明确区分；独立 Change 不套用不存在的 Issue 要求。

每个摘要关联规范标识、来源文档与章节、版本。规则缺失或映射不明时显示“暂未配置”或“待核实”，不得生成看似有效的强制要求。命令仅作说明，不在阅读入口执行。

### FR-003 完整原文阅读

从摘要可以定位到同版本的规范原文及对应章节，显示文档标题、项目归属、相对来源路径、版本及可用的更新时间。Markdown 标题、列表、表格、代码块和内部链接可阅读；危险 HTML、脚本和越权链接不能执行或读取。

返回摘要或看板时保留原阶段及阅读上下文。来源不存在、章节失效与无权限状态分别处理；无权限提示不泄露内容和敏感路径。

### FR-004 独立研发规范中心

项目工作区提供独立“研发规范”入口，组织为流程规范、专项规范与规范迭代日志。专项规范覆盖纳入清单的 API、数据库、UI、测试、安全、部署等文档。

支持按标题和正文关键词搜索、按分类或阶段筛选。搜索只覆盖当前项目授权内容，结果展示所属规范和来源版本，点击定位正文；无结果不等于没有规范。

### FR-005 同源与版本一致性

规范中心与阶段摘要共用规范目录、身份和版本信息；不得分别维护两套无关联正文。摘要可人工结构化维护或由受控索引产生，但要绑定来源版本；原文更新后旧摘要不能继续标记为最新。

草稿默认方案：以当前绑定项目的规范来源为准，不自动用平台模板覆盖或补齐项目规则；平台参考若后续纳入，应独立标注且不宣称在项目生效。来源清单建议覆盖 AGENTS.md、rules/、相关技能和治理标准，按明确清单纳入，不能无差别开放目录。

区分当前项目来源、可确认的生效版本与历史版本。不能仅凭文件更新时间、提交时间或日志存在就推断审批生效。未能确认时标注版本或生效状态待核实。打开或刷新时检查版本；检测到更新后提示重载，摘要、原文与日志关联按一致版本切换，不混用缓存。

### FR-006 规范迭代日志与追溯

读取纳入范围的 docs/spec-logs/ 日志，按时间倒序展示标题、变更时间、原因、变化摘要、影响阶段和关联规范；字段缺失显示未记录，不编造。

日志详情关联已知来源版本；有可读历史原文时可打开，无历史正文时明确说明仅有记录，不把当前原文冒充历史版本。日志记录与当前生效事实分别展示。首期追溯到文档和版本，不要求自动行级差异。

### FR-007 权限与只读边界

复用当前空间和项目读取授权。页面、搜索、直接链接、原文和历史版本均执行相同隔离；禁止跨项目同名路径串读、目录穿越和符号链接越界。不展示凭证、真实环境文件、运行时数据或本机绝对路径。

查阅不得写入规范源文件、Issue、Change、Sprint 或业务阶段；缓存和必要观测不视为规范编辑。权限撤销后不能通过旧链接或缓存继续获得受限内容。

### FR-008 加载与异常

覆盖加载中、空目录、缺少阶段映射、原文缺失、版本过期、无历史记录、无权限、读取失败和重试。个别文档失败不阻断其他规范；重试无业务写入。规范中心不可用不改变现有研发操作是否允许的判定。

## 5. UI 约束

阶段入口保持紧凑，摘要优先呈现业务要求；原文与日志按需展开。建议阶段摘要使用统一只读抽屉，规范中心提供分类目录和正文阅读区，具体布局由 req-complete 原型确认。

遵循 rules/ui-design.md 及既有设计 token、组件。覆盖 1440px、窄视口、深浅主题、长标题、长表格与代码块滚动；键盘可达、焦点返回、关闭与返回路径明确。阅读操作不增加无意义确认弹窗。

本次没有参考稿复刻输入，不创建 UI Reference Replication Contract，也不声称视觉验收通过。后续原型按 docs/standards/prototype-ui-acceptance.md 完成拆解、UI Contract、Skeleton、截图、样式及交互证据。

## 6. 验收方向

- AC-001：九阶段空列与有卡片状态都能查阅对应规范，已完成阶段说明正确。
- AC-002：摘要涵盖条件、产物、角色及分支，REQ/BUG 差异可辨认，不执行流转。
- AC-003：两个入口对同一规范展示相同版本，摘要定位到对应原文章节。
- AC-004：规范中心分类、搜索、阶段筛选及返回阅读可用，结果不越权。
- AC-005：日志可追溯已知版本，缺失历史内容或生效依据时明确标注。
- AC-006：原文更新触发摘要过期识别，刷新后不混用新旧内容。
- AC-007：跨项目、路径越界、直接链接、权限撤销和危险 Markdown 内容均受保护。
- AC-008：查阅不改变规范文件或研发状态；异常与观测失败不阻断既有主流程。
- AC-009：1440px、窄视口、主题及关键交互具有视觉与样式验证证据。

以上为 PRD 验收方向，详细用例与证据矩阵在 req-complete 补齐。

## 9. 本轮完善形成的评审方案

以下为可评审默认方案，不冒充用户逐项确认：以当前绑定项目为边界；初始目录清单只包含 AGENTS.md、rules 下 Markdown、被流程引用的技能 SKILL.md、被规则引用的 docs/standards 文档和 docs/spec-logs 日志。清单由受控配置定义，递归引用不自动放开权限，未知目录拒绝。

当前版本使用相对路径与内容指纹标识；可取得时附 Git 提交版本。存在未提交修改时展示工作区版本。没有明确生效记录则展示“生效状态待核实”，不自行推断发布或批准。首期历史原文仅查询可取得的版本记录，缺失不补造。刷新时校验指纹，摘要指纹不匹配时停用旧摘要并提示读取原文。

空间/项目的现有读取授权适用于目录、摘要、正文、搜索和历史；首期不新增角色或编辑权限。只读抽屉承载阶段摘要与原文，独立页面承载目录和日志。初始性能样本与证据约束见 acceptance.md。
