# 会话准备导航延迟修复评审

## 评审结论

approved，确认按限定机制安排常规修复。用户本轮授权评审，取代此前暂不推进评审的限制；不等于授权直接开发。严重等级维持high，不走hotfix：存在核心入口秒级延迟，但无数据丢失、越权或全站不可用证据。

## 根因与证据门禁

E2/E3调用路径、E15自然请求同ID计时、E16原路由准入正反例共同确认：同步重复读取治理快照处于导航关键路径，复用idle会话仍支付准备成本。16项证据门禁通过。当前采样归因不外推历史截图21.27秒的精确占比、唯一来源、数据库等待或所有动作；这些继续未知。

## 批准修复范围

1. 优先减少同一准备请求内重复源/投影快照读取；复用必须有明确版本与写入围栏，变更发生时重读或拒绝，不使用跨请求无界缓存。
2. 保留权限、对象生命周期、Sprint成员/状态、执行占用、待审候选、幂等、源投影一致性与关联对象恢复语义。已有/新会话、目标写动作和共享路径只读入口均回归。
3. 仅在证明恢复语义等价后收窄协调范围；不能为了达标跳过reconcile或提前返回未经校验的可发送会话。
4. 提供验证所需的请求阶段证据。现有观测不足时可用受控诊断；永久埋点需在后续Change明确字段、脱敏、成本与兼容影响。

不包含历史消息加载、消息提交、全仓快照系统重构、通用缓存平台或数据库架构调整。准备反馈可作为本范围体验补充，不能替代性能目标；超出上述范围应重新评估，不自动扩大修复。

## 性能目标与测量契约

以下为本次制定的验收目标，并非实测保证。依据现有自然请求约6.38–7.05秒且快照约97%的成本分布，要求显著降低用户等待；是否可达由修复后同条件实测证明，不用历史21.27秒作对照分母。

- 基准：固定部署资源、数据库、同规模治理树、对象状态、动作、认证与网络；记录版本、文件数/字节数、缓存状态及后台负载。原诊断规模约6818文件/20.2MB仅作参考，验收前冻结实际数据集，修复前后相同。
- 暖态：明确一次预热且不计入统计，前后各至少10个顺序有效请求。准备接口中位数≤2000ms、较基线中位数降低≥50%，最大值≤4000ms，三项同时满足；计时从服务端收到请求至响应发出，浏览器同ID关联复核。
- 导航体验：同一浏览器条件下，点击至Chat路由切换中位数≤2500ms、最大值≤4500ms；历史内容加载和Chat可交互时间另列，不混入本BUG阈值，不以提前跳转掩盖准备未完成。
- 冷态：仅清理本修复管理的进程/请求缓存，不宣称清除OS缓存；前后至少5个独立冷态样本，准备中位数≤4000ms、最大值≤6000ms，且较同条件基线不退化超过10%。
- 并发：同一数据集3个独立对象并发，前后各10批；报告单请求中位数与最大值，修复后均不得较基线退化超过10%，无新增5xx/锁错误/重复会话或动作；任一正确性失败直接不通过。
- 阈值适用基准规模和资源。数据规模/配置改变须重新固定对照；不达标先分析与返修，调整目标需要显式说明证据并重新评审，不能事后降低标准。
- 记录全部失败、取消、超时及离群样本；缺失值不填零，不剔除慢请求。只有有效请求计入时长统计，错误样本单独计数且不能用重试成功抹除。非故意错误用例出现新增失败则验收不通过。
