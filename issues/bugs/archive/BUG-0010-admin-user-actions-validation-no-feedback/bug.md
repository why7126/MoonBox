# 现象

用户管理页存在两类点击后缺少反馈的交互问题：

1. 编辑用户时，修改昵称、头像或角色后点击「保存」，在特定用户数据下可能没有任何可见响应。
2. 重置密码、冻结、解冻、删除确认弹窗中，未填写操作原因时点击「确认」，没有可见错误提示或下一步引导。

# 复现

## 编辑用户保存无反馈

1. 进入管理后台用户管理页。
2. 打开某个用户的编辑弹窗。
3. 修改昵称、头像或角色。
4. 点击「保存」。

触发条件倾向：已有用户的 `username` 不满足当前前端新增用户正则时，编辑态仍被用户名校验阻断。由于编辑态用户名输入框不可编辑且错误提示仅在新增态展示，用户无法知道保存被阻断原因。

## 确认操作空原因无反馈

1. 进入管理后台用户管理页。
2. 打开重置密码、冻结、解冻或删除确认弹窗。
3. 保持「操作原因」为空。
4. 点击「确认」。

当前确认按钮在操作原因不足 4 个字符时被禁用；空原因不满足错误提示展示条件，因此用户看不到“必须填写操作原因”的错误反馈。

# 期望 vs 实际

期望：

- 编辑态只校验可编辑字段；若保存被阻断，应展示明确、可见、可访问的错误提示。
- 操作原因为空或不足 4 个字时，应在弹窗内展示校验错误，并提示用户补齐原因。
- 重置密码、冻结、解冻、删除等审计敏感操作应保持原因必填，但不能以静默禁用造成“点击无响应”的体验。

实际：

- 编辑态保存仍受用户名合法性影响，而用户名不可编辑、错误提示也不展示。
- 操作原因为空时「确认」按钮被禁用，错误提示不会出现，用户感知为无响应。

# 影响范围

- 页面：管理后台用户管理页。
- 操作：编辑用户、重置密码、冻结用户、解冻用户、删除用户。
- 用户：后台管理员。
- 风险：阻断日常用户管理流程，降低审计操作可理解性；管理员可能误判为系统卡死、按钮失效或接口异常。

# 严重等级说明

严重等级建议为 `high`：

- 影响后台用户管理核心流程。
- 复现路径短，用户感知明显。
- 后端约束本身合理，主要问题在前端没有提供可见反馈，修复面集中但需要补充交互与测试。
