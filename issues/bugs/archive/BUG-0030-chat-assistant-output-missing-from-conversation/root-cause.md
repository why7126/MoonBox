# Chat 助手正文缺失根因分析与补证清单

## 根因状态

当前代码的故障机制已由隔离合成轮次确认：助手输出事件先提交，执行器在正常收尾前断连时，轮次进入 unknown 而助手消息未写入；权威终态恢复后仍未补写消息。2026-10-05 原 T1/T2 数据已删除，无法证明历史两轮确实由此机制触发。此前跳过根因确认的评审例外仅为历史工作流事实，本次确认依据是下述直接复现证据。

## 现象

历史 capture 记录同一会话的已停止轮次 T1（15:47:48）和状态未知轮次 T2（21:16:05）轨迹已有助手文字而对话无正文。221 与 16 是当时已读取的全部类型事件数，不是助手输出事件数。本轮未重新复现历史界面。

## 候选根因与已排除假设

| 假设 | 当前结论 | 确认或排除所需证据 |
|---|---|---|
| 输出已保存，异常发生在收尾写消息之前 | 当前机制已验证；历史路径未知 | E10；历史 T1/T2 的事务记录已无法取得 |
| unknown 恢复只补终态，未补助手正文 | 当前机制已验证；历史路径未知 | E11；原 T1 是否经过恢复无法取得 |
| 消息已存在但分页或前端展示遗漏 | 合成轮次已排除；历史轮次无法排除 | E10 的数据库与消息 API 均为 0；原数据已删除 |
| 所有已停止轮次必然无助手正文 | 已排除 | E12 的正常停止对照写入并返回助手消息 |
| 助手完全没有输出 | 与历史记录不符 | E1 记录存在助手文字；仍不代表存在最终答案或业务已完成 |

## 已确认根因

当前代码在“输出增量已记录、正常收尾前断连”的触发条件下，`execution.output` 已单独提交，而助手正文仅保存在 `run_claim` 的局部 `reply`，尚未进入收尾事务；异常转为 unknown 后，`reconcile_unknown` 只恢复终态及工具事件，不从已有输出事件或权威轮次补写 assistant 消息。消息 API 只查询 `chat_messages`，因而对话正文为空。E10–E12 在隔离 SQLite 中把同轮次事件、消息、状态、恢复事件和 API 串联验证，确认的是当前故障机制；原历史两轮的实际断点仍不可判定。

## 自主补证与具体阻碍

2026-10-08 通过 Firefox 自主访问本地产品，搜索历史会话；又对当前 SQLite、现存 Chat 快照及执行器历史索引做只读聚合查询，结果见 E6–E9。当前可访问历史数据均未包含 T1/T2。随后执行 E10–E12 的隔离合成测试，未读取认证凭证、历史消息正文、原始事件 payload 或执行器 item_json，未重放归档操作。

用户确认历史 Chat 数据已删除，P1–P3 的原实例证据无法再从该历史数据源取得。E10–E12 已验证当前代码机制及正常停止对照，但不能反推 T1/T2 实际走过哪条路径。

## 修复方向

修复应在异常及恢复路径保留同轮次已保存输出的可读性，并对部分内容、未知终态与幂等恢复分别处理；不得仅因文字存在就标记轮次完成。原历史轮次的路径不作为实现已验证前提。

## 验证闭环

隔离合成机制复现及正常终结对照已完成，2 个测试通过；这是修复前基线，未进行修复后验收。原实例证据链因数据删除无法补齐；完整验收矩阵见 acceptance.md。
