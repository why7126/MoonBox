# BUG-0016：需求中心与 MD 文档加载异常

## 现象

1. 用户反馈需求中心刷新缓慢，需要等待很久才能加载出来。
2. MD 文档右侧抽屉打开、加载缓慢，最新反馈为当前甚至无法加载出来。

按用户明确要求，两项现象保留在同一 BUG 中；其读取入口共用项目快照链路，但不据此认定所有性能问题只有一个原因。

## 复现步骤

### 用户操作入口

1. 登录并进入已绑定项目的需求中心。
2. 刷新页面或点击刷新，观察看板恢复可用的等待时间。
3. 点击卡片中的 MD 文档，观察右侧抽屉加载状态、错误和文档可读性。

### 已执行的本地接口对照

1. 使用当轮工作区治理目录的临时副本、独立 SQLite 数据库及合成账号，以真实登录获得会话；通过应用原生 ASGI 入口调用真实路由，无业务接口 Mock。
2. 依次读取 `/api/v1/requirement-center/projects`、`/api/v1/requirement-center/context` 和 `/api/v1/requirement-center/issues/BUG-0016-capture/documents/capture.md`；项目参数使用隔离测试绑定。
3. 保持原始副本，记录响应状态、错误码和耗时。
4. 仅在临时副本中将 `issues/requirements/_registry.yaml` 的 `related_change: add-requirement-center-change-visibility` 从四格缩进调整为与相邻字段一致的两格缩进。
5. 重复同样的接口请求两轮，读取已有 `requirement_center.read_timing` 日志做分段对照。
6. 测试完成后清理隔离环境；原工作区文件未因取证而修复。

## 期望与实际

| 场景 | 期望 | 已观察到的实际 |
|---|---|---|
| 需求中心刷新 | 正常显示内容，等待时间可接受；性能验收阈值在完善阶段明确 | 用户反馈长时间等待；原始副本接口返回 503；缩进纠正后接口为 200，耗时 1.556 秒、2.432 秒 |
| MD 文档抽屉 | 能加载并阅读选中文档，失败反馈可定位 | 原始副本接口返回 503；缩进纠正后接口为 200，耗时 0.526 秒、0.904 秒 |
| 项目目录 | 返回用户可访问项目 | 原始副本返回 200，耗时 0.026 秒 |

以上为本地应用接口耗时，不是浏览器端到端耗时，也不是 Docker 或用户部署环境的基准。

- 无法加载：对当轮本地原始快照，直接原因已确认；尚未确认该错误由哪个写入操作引入。
- 加载缓慢：已确认存在全量处理开销及本地秒级读取；尚未证明用户部署中的全部长时间等待均由此引起。
- 浏览器渲染、Docker 挂载、反向代理、并发与实际项目体量未纳入此次对照，不宣称已完成这些层面的复现。
- 原始取证仅保留于会话工具结果；临时环境已清理，未将原始日志、账号凭据或文件正文落入仓库。

## 影响范围

- 受影响项目的需求中心看板刷新及 MD 文档阅读；需求注册表错误可影响同项目 BUG 文档，不局限于出错的 REQ 卡片。
- 所有经过同一 `ProjectReader` 快照流程的读取入口存在共同依赖；其他入口的实际失败范围需后续回归确认。
- 正常快照下，即使项目未变化或只读取单份 MD，仍重复全量读取、解析与临时目录操作；轮询会持续触发该开销。
- 本轮没有数据丢失、越权或跨项目影响证据。

## 严重等级说明

保留现有 `medium`，与 trace 和 capture 一致。本地已证实核心阅读链路可被阻断，后续应结合实际部署的影响用户数、发生频率、持续时间及替代入口评估是否升级；本次不凭隔离测试直接调整严重等级。

## 后续完善范围

- 明确注册表写入前解析校验、写入一致性和错误定位方案；尚未确认错误来源，不指定责任写入器。
- 评估快照复用、减少单文档读取的全量处理以及轮询策略；保留成员权限、对象授权、写入版本围栏和快照一致性边界。
- 验收覆盖畸形注册表错误、正常看板和 MD 读取、无变更重复读取、文件变更后可见性、权限失效及并发写入保护。
