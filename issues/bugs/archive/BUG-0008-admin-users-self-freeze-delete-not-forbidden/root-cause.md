# 根因分析

## 直接原因

管理后台用户状态变更接口在执行冻结和删除时，只校验调用方是否为后台管理员，并把 `actor["id"]` 作为审计字段传入状态更新逻辑；接口层没有在目标用户 `user_id` 与当前登录用户 `actor["id"]` 相同时提前返回 `403 Forbidden`。

前端用户管理操作列也只根据 `is_system_superadmin` 和 `status === "已删除"` 隐藏操作，没有把 `currentSessionUser.id === user.id` 作为冻结、删除危险操作的禁用或隐藏条件。

## 根本原因

用户生命周期治理只覆盖了“系统内置超级管理员不可操作”和“已删除用户不可恢复”等目标账号保护规则，没有把“当前会话主体不得冻结或删除自己”定义为后端强制权限边界和前端交互约束。

该边界不能仅依赖前端隐藏按钮；后端必须作为最终权限裁决点，确保任何直接 API 调用、旧前端缓存、自动化脚本或恶意请求都无法让当前登录者冻结或删除自己的账号。

## 触发条件

- 当前登录用户是非系统内置后台管理员。
- 用户管理列表包含当前登录账号。
- 当前账号状态为 `待激活`、`正常` 或其他现有逻辑允许进入冻结/删除的状态。
- 调用 `POST /api/v1/admin/users/{current_user_id}/freeze` 或 `DELETE /api/v1/admin/users/{current_user_id}`。
- 前端渲染当前账号行时未隐藏或禁用冻结、删除操作。

## 分类

- 类型：code / security / authorization / frontend-guard
- 影响端：管理后台 Web、后台用户管理 API
- 影响能力：后台用户冻结、后台用户删除、会话撤销、账号生命周期管理
- 关联测试：API 集成测试、前端用户管理回归测试

## 结论

这是权限边界缺失导致的安全与可用性缺陷。修复应在后端冻结、删除入口增加当前用户自操作拒绝，并在前端当前账号行隐藏或禁用冻结、删除操作；同时补充 API 与前端回归测试，避免未来仅保留系统超级管理员保护而遗漏普通后台管理员自保护。
