# 依赖子交付与迭代承接实践

适用于一个完整需求仅交付必要依赖、后续仍需完整产品验收的情况。来源为[迭代复盘](../retrospectives/sprint-015-retrospective.md)，不替代用户范围授权、Sprint容量或归档准入。

1. 子Change建立独立AC、完整范围说明和Issue AC映射；当前子范围所有门禁通过后才能归档。父需求保持partial和未完成AC，不能以子交付覆盖全部需求。
2. 剩余范围经用户批准后明确目标迭代、估算和依赖；旧迭代保留已交付Change、原估算和源需求关系，新迭代只估算剩余工作。活动迭代数量限制仍生效。
3. 当前需求iteration、注册表和看板指向承接迭代；已归档Change与不可变验收证据留在原归属。只修正可变文档入口，不批量替换manifest/checkpoint路径。
4. 当前工具对跨迭代旧事件重放仍有归属漂移风险。不要将重复执行旧sprint.archive当成无害刷新；先预演，检查转出需求是否被清空或回退，按当前迭代聚焦同步并复核。此为已知限制，不是已修复保证。
5. 范围工具写入后检查YAML顶层键唯一、实际解析需求列表、主Scope和派生表；工具退出0不能替代这些检查。新模板为派生表提供空槽，由同步器填充内容。
6. 产品测试、用户条件式归档授权、生命周期关闭和生产部署分别记录；后续规划不修改原测试事实。

验收关注：父需求未被误关闭、旧Change不重复交付、新迭代容量正确、四类当前态入口一致、历史附件哈希不变、旧事件重放不破坏当前归属。最后一项仍待S15-A001修复验证；不得因本实践已写入就宣称门禁已实现。
