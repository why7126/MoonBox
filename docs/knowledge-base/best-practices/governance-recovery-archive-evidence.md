# 治理恢复与归档验收证据分层实践

适用于多文件治理动作、阶段收尾、持久化恢复和包装命令归档。来源为[迭代复盘](../retrospectives/sprint-010-retrospective.md)、[恢复记录事故](../incidents/20261019-review-operation-record-contract.md)和[归档证明事故](../incidents/20261019-archive-wrapper-completion-proof.md)，不替代各命令权限及验收计划。

## 实践步骤

1. 明确生产者在准备成功时承诺哪些基线与操作记录，消费者启动前检查相同契约。单文件原子写不等于多文件事务；损坏或缺失记录保留诊断，不能补空记录绕过。
2. 分开记录轮次终态、业务成果和当前展示。核对对象身份、唯一应用、文件状态与工作流检查；模型文字或包装脚本名称不是完成证明。
3. 验收计划分别安排首次正常、失败拒绝、原执行恢复和重启回读。隔离样本执行时暂停相关治理写入；不并行迁移 Issue、归档 Change 或关闭 Sprint。
4. 合成故障说明覆盖边界；真实轮次提供运行证据；部署指纹说明运行版本；视觉与 computed style 说明展示事实。四层结论分别签认。
5. 保留原始 manifest、失败/停止/未知轮次和旧证据摘要。修复可变当前态入口；附件变化仅走现有受控补证，不能手改哈希让检查通过。
6. 归档后核对读取侧状态与路径；恢复仅重核验原执行，不重放成功副作用。后续合法变更可能使旧证明失效，应报告具体原因。

## 使用边界

BUG-0050 的拒绝与恢复不替代 BUG-0051 的独立样本；既有 stopped 轮次的业务成果被核验也不等于轮次 completed。真正的成功条件由对应计划定义，不能一概以文件存在判定。

## 后续验收清单

- 基线、操作、应用与归档目标身份一致。
- 正常首次完成、失败拒绝和原执行恢复有各自证据。
- 共享治理写入串行，重复调用没有重复应用或模型调用。
- 当前态引用可解析，原始历史证据保留。
- API、DB、权限、观测或 UI 变化按实际影响同步文档和测试。
